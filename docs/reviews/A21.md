## 처리 — Critical/Major 수정 상세

**#1 (Monaco 텍스트 유실)**: `src/registry/kind-registry.ts`의 `KindRendererFactory`를
`(targetId, ctx: {params, updateParams}) => ...`로 확장했다(`targetId`는 첫 위치
인자로 유지 — #6이 그 이유). `updateParams`는 해당 패널의 dockview params에 patch를
merge하며 `toJSON()`/`fromJSON()`이 그대로 보존한다. `src/presets/file-preset.ts`가
`params.value`를 초기 콘텐츠로 읽고, `TextEditorView`에 새로 추가한
`onDidChangeContent()` 콜백으로 편집마다 `updateParams({value: view.getValue()})`를
호출한다.

**#2 (숨은 dirty 종료 감지)**: `src/core/editor.ts`에 리소스 종류에 무관한 순수 함수
`snapshotHasDirtyPanels(snapshot)`을 추가했다(직렬화 JSON의 `params.isDirty`만 읽음).
`src/main.ts`에 `WorkbenchApp.confirmQuit()`을 신설해 `editor.confirmQuit()`(보이는
워크스페이스) 통과 후 `hasHiddenDirtyEditorState()`로 `folderWorkspaceByTab`의 각
항목과(워크스페이스 모드일 때) `sharedEditorSnapshot`을 검사한다. 양쪽 호스트의
윈도우 close 핸들러가 `editor.confirmQuit()` 대신 `app.confirmQuit()`을 호출하도록
바꿨다.

**#7 → #10 (Save의 실제 의미)**: 두 단계로 수정했다.
1. (2회차 대응) `choice !== 'cancel'`을 `choice === 'discard'`로 바꿔, 저장할 수
   없는 Save를 Don't Save와 동일시하던 조용한 데이터 폐기를 막았다 — 단, 이 시점에는
   Save가 Cancel과 동일하게 "아무 일도 안 하고 열려 있음"으로만 동작했다.
2. (3회차 대응) `saveHiddenDirtySnapshots()`를 신설해 Save를 진짜로 만들었다. 숨은 각
   dirty 스냅샷을 **하나씩** `editor.getApi().fromJSON()`으로 잠깐 살아있는 에디터에
   올리고, 그 안의 dirty 패널을 `kindRegistry.save()`(보이는 저장과 동일 경로 —
   dockview가 패널 id를 직렬화 왕복에서 보존하므로 같은 id로 saveable이 재등록됨)로
   저장한다. `confirmQuit()`이 `true`를 반환하는 즉시 앱 전체가 종료되므로, 이 과정이
   일으키는 화면 깜빡임이나 원래 보이던 내용을 되돌리지 않는 점은 문제가 되지 않는다
   (그 이후로 아무것도 다시 렌더링되지 않는다).

**#8 (dirty 기준점 유실)**: `src/core/texteditor.ts`의 `TextViewOptions`에
`savedValue?: string`를 추가했다(생략 시 `value`로 폴백 — 신규 오픈 동작은 그대로).
생성자가 `this.savedValue = options.savedValue ?? options.value`로 바뀌었고, 공개
접근자 `getSavedValue()`를 추가했다. `file-preset.ts`는 이제 `params.value`와
`params.savedValue`를 **둘 다** 복원 시 읽고, 콘텐츠 변경 시와 저장(`save()`) 시
**둘 다** 다시 params에 쓴다.

## 유효하지 않은 지적과 반박 근거

**#12 (Minor, 편집마다 전체 버퍼 복사)**: 리뷰어 자신이 "현재 placeholder 프리셋
범위에서는 치명적이지 않다"고 명시했고, 이 세션은 디바운스를 검토했으나 의도적으로
적용하지 않기로 했다 — 디바운스는 패널이 dispose되거나 모드가 전환되는 시점에 아직
flush되지 않은 마지막 몇 글자를 유실할 위험을 새로 만든다. 이는 정확히 이번 검토
3회차 전체가 잡아 온 것과 같은 종류의 버그(직렬화 시점에 최신 편집 내용이 반영 안
됨)이므로, 미미한 성능 이득을 위해 그 위험을 다시 들여오지 않기로 판단했다. `file-
preset.ts`가 명시적으로 "INTENT 7: 최소 예시, 실제 파일 I/O 아님"이라고 밝히는
프리셋이라는 점도 이 판단의 근거다.

## 미해결 · 남은 위험

- Minor #12(편집마다 params 갱신 비용)는 의도적으로 남겨 두었다 — 위 반박 근거 참조.
- `saveHiddenDirtySnapshots()`는 숨은 스냅샷을 하나씩 순서대로 살아있는 에디터에
  올려 저장하므로, 저장할 스냅샷이 여러 개면 그 수만큼 `fromJSON()`을 반복한다 —
  일반적인 사용(폴더 탭 소수)에서는 문제 없지만, 탭이 매우 많고 전부 dirty인 극단적
  상황의 체감 지연은 측정하지 않았다.
- Phase 4(A19)와 마찬가지로, `file-preset.ts`는 명시적으로 실제 파일 I/O가 아닌
  최소 예시 프리셋이다(INTENT 7). 이번 Phase가 고친 것은 "이 프리셋이 params를 통해
  자기 콘텐츠를 왕복시키는 계약"이며, 실제 파일을 다루는 미래의 진짜 프리셋이 이
  계약(`KindRendererContext.params`/`updateParams`)을 그대로 재사용할 수 있는지는
  검증 범위 밖이다.
