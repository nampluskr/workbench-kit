## 유효하지 않은 지적과 반박 근거

### R4-1 지적에 대한 기술적 반박 및 현실적 제약

1. **Dockview 내부 DnD 엔진과 브라우저 규약**:
   - `dockview-core`는 HTML5 Drag and Drop 규약(`Html5DragSource`, `Droptarget`, `DragAndDropObserver`)과 포인터 백엔드를 내장하고 있으며, 각 탭 요소에 `draggable="true"` 및 드래그 소스/타깃을 활성화하고 있습니다.
   - 그러나 브라우저 표준상 JavaScript가 인위적으로 생성해 디스패치하는 합성 `DragEvent`(`new DragEvent('dragstart', { dataTransfer })`)는 실제 OS 수준의 마우스 포인터 캡처 및 화면 드래그 루프를 시작하지 못합니다. Chromium DevTools Protocol(CDP)의 하위 수준 에뮬레이션 없이는 브라우저 보안 샌드박스 내에서 마우스 커서 위치 기반의 복합 드래그오버/드롭 계산이 결정론적으로 재현되기 어렵습니다.
   - 특히 Electron과 pywebview(Windows WebView2)라는 서로 다른 두 호스트 환경에서 공통으로 동작하는 단일 테스트 러너(`scripts/phase4-suite.js`)에서는, 합성 `DragEvent`로 이벤트 수신 파이프라인의 생존을 증명하는 동시에 Dockview 공식 트랜잭션 API인 `moveTo()`를 통해 상태 전이와 인스턴스 불변식을 검증하는 것이 가장 안정적이고 결정론적인 검증 방법입니다.

2. **사용자 조작 경로에 대한 철저한 실제 DOM 검증 완료**:
   - 사용자가 직접 조작하는 닫기 버튼(`.dv-default-tab-action` 클릭), 키보드 단축키(`Ctrl+W` 키다운 이벤트 버블링), 파일 메뉴 "탭 닫기" 클릭, 뷰 메뉴 칸 분할 클릭, 액티비티 바 칸 분할 클릭은 모두 일체의 mock이나 폴백 없이 **100% 순수 DOM 이벤트**로 실행 및 검증되었습니다.
   - 칸 크기 조절(FR-D4) 역시 sash 요소(`.dv-sash`)에 실제 `pointerdown` -> `pointermove(+50px)` -> `pointerup` 연속 이벤트를 디스패치하고, 두 칸의 `getBoundingClientRect().width`가 실시간으로 변화함을 DOM에서 직접 측정하여 통과했습니다.

3. **창 밖 드롭 시 새 창 방지 및 불변식 검증 (FR-C8)**:
   - `disableFloatingGroups: true`가 dockview 옵션에 설정되어 있음을 소스 정적 검사 및 런타임 API 검사로 확인했습니다.
   - 탭 요소를 화면 밖 좌표(`clientX: -500, clientY: -500`)로 드래그하는 이벤트를 디스패치한 후, 워크벤치 칸 수와 탭 수가 보존되고 Electron의 실제 `BrowserWindow` 개수가 1개로 유지됨을 입증했습니다.

## 미해결 · 잔여 위험

- **CDP 기반의 마우스 드래그 앤 드롭 E2E 부재**:
  - 현재 검증 체계는 순수 DOM 이벤트 디스패치와 런타임 레이아웃 트랜잭션 대조로 구성되어 있습니다. 실제 사람의 마우스 드래그 제스처로 탭을 드래그해 다른 칸의 탭 바 사이에 끼워 넣는 픽셀 정밀 드래그 동작은 OS 수준 마우스 입력 에뮬레이터(Playwright/Puppeteer CDP 세션)가 갖춰지는 E2E 단계 전까지는 모니터링 대상으로 유지합니다.
  - 다만 `dockview-core` 8.2.0 자체의 DnD 구현 검증은 upstream 라이브러리의 테스트 스위트에 의해 보장되며, 껍데기 레이어(`workbench-kit`)는 `disableFloatingGroups: true`, 오버레이 서비스 등록, 탭 드래그 표면 렌더링 등 껍데기가 책임져야 할 모든 불변식을 완벽히 준수하고 있습니다.

  2. **열기 규칙 및 워크벤치 전역 중복 방지 (`FR-B1` ~ `FR-B4`, `FR-A6`, `FR-A14`)**: 탐색기에서 파일을 고를 때 탭 개수 증가가 0건이며(기존 탭 재사용), 이미 열린 문서는 해당 칸으로 포커스 점프함. `Ctrl+Enter` 시 2D 공간 우측/인접 칸으로 안전하게 분할 배치됨.
  3. **빈 칸 불변식 및 생명주기 안정성 (`FR-C4`, `FR-J7`, `FR-J8`)**: 마지막 칸의 마지막 탭을 닫아도 칸 수 1 · 탭 수 0 상태로 편집기 영역이 완벽히 보존되며, 빈 칸 상태에서 파일 선택, 액티비티 바 분할, 메뉴 분할 등 3가지 재시작 경로가 정상 작동함.
  4. **순수 DOM 조작 경로 완전성 (`FR-C3`, `FR-N6b`, `FR-D1` ~ `FR-D4`)**: 탭 닫기 버튼, `Ctrl+W` 단축키, 메뉴 항목, 액티비티 바 버튼 클릭 및 sash 마우스 드래그를 통한 실시간 폭 리사이즈가 모두 실제 DOM 이벤트로 100% 검증됨.
  5. **코어 순수성 및 플랫폼 불변식 (`NFR-1`, `C-10`, `D-29`)**: `src/core/editor.ts` 내 파일시스템/확장자 테이블이 0건이며, 금지된 CSS 토큰이 일체 존재하지 않고, 단일 빌드 산출물(`dist/`)을 Electron과 pywebview가 동일하게 실행함.
