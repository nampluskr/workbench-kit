**Why this prevents completion**

This is substantially the same unresolved Round 2 Major finding. The suite demonstrates internal Dockview operations, not that users can perform the required operations in either host.

## Major 2 ? FR-D7 has the wrong oracle and performs only three stress-test splits

**Exact Reproduction Condition**

Immediately before the stress section, the preceding tests have already created five groups. The loop then runs only until the total reaches eight:

```js
while (editor.getGroupCount() < 8) {
  editor.splitActiveGroup('right');
}
```

Thus the alleged ¡°8 Splits¡± test performs only three additional splits and asserts eight panes: [phase4-suite.js](/D:/projects/workbench-kit/scripts/phase4-suite.js:298).

FR-D7 explicitly requires starting with a pane, performing **eight split operations**, and ending with **nine panes**: [SPEC.md](/D:/projects/workbench-kit/docs/current/SPEC.md:86).

An implementation that rejects every split after the eighth pane would pass the current assertion while violating the specification.

**Violated Clause / Specification ID**

- FR-D7
- WK-019
- PLAN Phase 4 all-37-cases completion condition

**Recommended Fix**

Reset to exactly one pane, record the initial count, perform an explicit eight-iteration loop, and after every iteration assert:

- No exception or rejection
- Pane count equals `initial + iteration`
- All groups remain attached and measurable

The final count must be nine.

**Why this prevents completion**

The suite positively certifies a result different from the normative result. FR-D7 therefore has no valid acceptance evidence.

## Major 3 ? Lifecycle timer continuity is masked by a shared counter

**Exact Reproduction Condition**

Every renderer¡¯s interval increments that same value, and every renderer returns it through `getTimerTicks()`: [phase4-suite.js](/D:/projects/workbench-kit/scripts/phase4-suite.js:164), [phase4-suite.js](/D:/projects/workbench-kit/scripts/phase4-suite.js:173).

- Inactive-tab continuity: [phase4-suite.js](/D:/projects/workbench-kit/scripts/phase4-suite.js:198)
- Cross-pane continuity: [phase4-suite.js](/D:/projects/workbench-kit/scripts/phase4-suite.js:221)

This recreates precisely the attack-focus problem: a synthetic aggregate supplies the expected observation instead of the tested instance.

**Violated Clause / Specification ID**

- FR-E2 and FR-E5
- D-24
- WK-022
- PLAN¡¯s requirement to reproduce the live-instance lifecycle experiment: [PLAN.md](/D:/projects/workbench-kit/docs/current/PLAN.md:114)
- Phase 4 attack focus against stubbed lifecycle counts: [PLAN.md](/D:/projects/workbench-kit/docs/current/PLAN.md:226)

**Recommended Fix**

Create `timerTicks` inside each factory invocation and close over that renderer-local counter. Record the original view¡¯s tick value immediately before and after each transition. Also confirm that the background renderer has a distinct counter and cannot affect the original view¡¯s observation.

**Why this prevents completion**

Creation identity and DOM-state checks are meaningful, but the required timer-continuity evidence is currently a false-positive oracle.

## Major 4 ? Cross-host verification does not enforce the claimed 73-assertion contract

**Exact Reproduction Condition**

Delete matching assertions from `phase4-suite.js` in both hosts while leaving the remaining assertions successful. Verification still passes because it checks only:

- Pywebview¡¯s returned `success`: [verify-phase4.mjs](/D:/projects/workbench-kit/scripts/verify-phase4.mjs:155)

**Violated Clause / Specification ID**

- SPEC common cross-host adjudication rule: [SPEC.md](/D:/projects/workbench-kit/docs/current/SPEC.md:23)
- FR-H1¡¯s requirement to compare the complete applicable result table: [SPEC.md](/D:/projects/workbench-kit/docs/current/SPEC.md:132)

**Recommended Fix**

**Why this prevents completion**

Host-neutral execution exists, so Round 2 Major 1 is directionally fixed. However, the verifier cannot prove that either host executed the complete suite it claims to have executed.

## Minor 1 ? Lifecycle diagnostic metadata grows permanently

**Exact Reproduction Condition**

Every renderer creates an entry in `panelLifecycleStats`: [editor.ts](/D:/projects/workbench-kit/src/core/editor.ts:204), [editor.ts](/D:/projects/workbench-kit/src/core/editor.ts:207). Disposal removes the renderer from `contentRenderers`, but never removes its statistics entry: [editor.ts](/D:/projects/workbench-kit/src/core/editor.ts:236).

The Round 2 strong renderer/DOM retention problem is fixed, but one metadata record and stamp string remain for every historical panel.

**Violated Clause / Specification ID**

- Quality/lifecycle expectations associated with FR-E3 and WK-022
- This is not currently a direct renderer-instance retention violation.

**Recommended Fix**

Move lifecycle accounting into test-only instrumentation or provide a bounded/explicitly disposable diagnostics store. If post-close statistics are needed, have the test subscribe to disposal events and retain them outside the production controller.
