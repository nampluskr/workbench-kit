# PLAN — workbench-kit

## 이 순서에 걸린 두 가지 규칙

**두 갈래는 갈라 붙이지 않는다(D-6).** Electron을 먼저 만들고 pywebview를 나중에
붙이는 Phase는 없다. Phase 1이 두 갈래를 동시에 세우고, Phase 2 ~ 6은 갈래를 모르는
웹 코드만 늘린다. 산출물이 한 벌이므로(D-25) 갈래 차이가 들어올 자리가 구조적으로
없다. 갈래마다 다른 코드가 실제로 있는 곳은 Phase 1(빌드·창 띄우기)과 Phase 2의
프레임리스 창 조작뿐이다.

**모든 Phase의 완료 조건은 두 갈래에서 각각 판정한다**(`SPEC.md` 1절 공통 판정 규칙).
Phase마다 반복해 적지 않고, Phase 7이 `FR-H1`으로 133건 전건을 대조한다.

**반입은 그 기능 Phase 안에서 한다.** "라이브러리 붙이기" Phase를 따로 두지 않는다 —
반입이 곧 그 Phase의 구현이기 때문이다(D-2). codicons·seti·vscode-icons는 Phase 2,
`dockview-core`는 Phase 4, monaco는 Phase 6이다. 라이선스 본문은 반입한 Phase에서
함께 넣고, Phase 7이 반입 라이브러리 다섯을 한 번에 센다.

### 필수 통과 Phase

**Phase 1 · Phase 4 · Phase 5 · Phase 7.** 이 넷은 미해결 Critical이 남아 있으면
다음 Phase로 넘어가지 않는다. 나머지(Phase 2 · 3 · 6)도 검증은 하되 진행을 막지
않으며, 미해결 지적은 기록만 남기고 Phase 7의 전건 대조에서 다시 걸린다.

넷을 고른 이유는 각각 다르다 — Phase 1은 되돌리는 비용이 가장 크고(여기가 어긋나면
이후 전 Phase의 "두 갈래에서 각각 판정"이 성립하지 않는다), Phase 4는 수명 조건이
시험 통과와 실제 동작이 가장 쉽게 갈리는 자리이며, Phase 5는 이 프로젝트의 존재
이유인 "코어를 고치지 않고 꽂힌다"가 판정되는 곳이고, Phase 7은 버전 마감 게이트다.
