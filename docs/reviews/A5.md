## 미해결 · 남은 위험

### R2-1 (Critical) — `window.__workbenchApp` 전역이 여전히 완전 접근을 제공한다

**재현 조건**
```js
const app = window.__workbenchApp;
app.editor.addNewTab();
app.editor.closeActiveTab();
app.menu.setAction('view:zen-mode', () => console.log('hijacked'));
app.menu.triggerItem('help:about');
```

**위반 조항**: FR-I8, FR-I9, FR-I11, C-9, D-19, D-31

**기술적 배경과 선택지**

- `window.__workbenchApp`은 Phase 1부터 있었고, Phase 1~4의 **고정(freeze)된** 시험 하네스(`phase2/3/4-suite.js`)가 셸 내부 동작(탭 생명주기, 트리 키보드, 창 조작 등)을 검증하려고 이 전체 객체에 깊이 접근한다. 이 전역을 제거하거나 좁히면 이미 서명 완료된 Phase 1~4 계약이 깨진다.
- `window.__workbenchAppSurface`(이번에 신설한 좁은 표면)는 실제로 탭/칸 조작 수단이 0개이고 메뉴 제어 수단이 0개임을 런타임으로 확인했다(`P5-FR-I8-SURFACE-*`). 그러나 Codex의 지적대로, **두 전역이 같은 전역 스코프·같은 JS 실행 컨텍스트에 존재하는 한, "문서화된 표면만 쓰라"는 것은 관행(convention)이지 강제(enforcement)가 아니다.**
- 이 프로젝트 자체가 `INTENT.md` 4절에서 "설치형 라이브러리·패키지가 아니라 복사해서 쓰는 템플릿"으로 명시하고 있어, npm 패키지의 `private`/모듈 경계 같은 진짜 캡슐화 수단이 애초에 없다 — 앱 코드는 항상 `src/core/*.ts` 소스 전체에 접근할 수 있는 같은 저장소 안에 있다. 즉 "런타임에서 절대 벗어날 수 없는 표면"은 이 아키텍처에서 애초에 성립 불가능하고, 성립 가능한 것은 "관행적으로 무엇을 문서화된 확장점으로 부르는가"뿐이다.

**선택지** (사람 판단 필요):
1. **현재 상태 승인**: `window.__workbenchAppSurface`를 FR-I8의 공식 판정 대상으로 삼고, `window.__workbenchApp`은 "Phase 1-4 고정 시험 전용, 실제 앱이 참조하도록 의도되지 않음"이라는 문서화된 관행적 제약으로 받아들인다.
2. **`window.__workbenchApp` 제거**: Phase 1~4의 `phase2/3/4-suite.js`를 전부 `window.__workbenchAppSurface`(또는 그에 상응하는 새 깊은 시험 전용 훅)로 재작성 — Phase 1~4의 "고정 계약"을 다시 여는 대규모 작업이며 별도 승인·별도 시간이 필요.
3. 그 밖의 방법(예: iframe/워커 격리 등 이 프로젝트의 "가벼운 템플릿" 성격과 충돌하는 더 무거운 구조 변경) — 제안하지 않음.

### R2-3의 잔여 한계 — 활동 표시줄·탭 줄의 실제 키보드 활성화는 합성 이벤트로 증명 불가

`P5-NFR7-NATIVE-BUTTONS`는 "네이티브 `&lt;button&gt;`이고 tabindex로 배제되지 않았다"까지만 확인한다. 진짜 `Tab` 포커스 후 `Enter`/`Space`가 클릭으로 이어지는 것은 브라우저의 신뢰된 입력 전용 기본 동작이라 스크립트로 재현할 수 없다 — Playwright/CDP 수준의 실제 OS 입력 에뮬레이션이 있어야 하며, 이는 Phase 4(A4)가 실제 드래그 앤 드롭에 대해 이미 인정한 것과 같은 종류의 한계다.
