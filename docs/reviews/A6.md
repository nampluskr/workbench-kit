## 미해결 · 남은 위험

### R3-1 (Critical) — pywebview가 확인 타임아웃·저장 실패·예외 시 동의 없이 닫힌다

**재현 조건**
1. pywebview에서 더러운 탭을 연다.
2. File > Exit 또는 네이티브 닫기를 요청한다.
3. (a) 확인 창에 약 10초간 응답하지 않는다 — 폴링 루프가 만료되며 `window.destroy()`가
   호출된다. 또는 (b) "저장"을 선택했는데 등록된 저장 핸들러가 reject한다 — JS의
   `catch`가 이를 `'yes'`로 바꿔 즉시 파괴한다. 또는 (c) `evaluate_js` 자체가 예외를
   던진다 — 바깥 `except` 블록이 무조건 파괴한다.

**위반 조항**: FR-L6, D-28("취소: 닫지 않는다" 및 조용한 유실 금지), Phase 6 완료 조건

**기술적 배경**

`request_confirmed_close()`는 재귀 방지(Round 2 Critical)는 올바르게 고쳤으나, 세
가지 경로(타임아웃/저장 실패/예외) 모두 "동의를 못 받음"을 "닫아도 됨"으로 처리한다.
현재 수용 시험은 이 경로들을 노출하지 않는다 — Cancel 시험은 1초 이내에 응답하고,
긍정 경로(저장 성공/저장 안 함) 시험은 `phase6-suite.js`에서 `editor.confirmQuit()`를
직접 호출해 실제 pywebview 브리지 왕복을 타지 않는다.

**결정 (사용자, 2026-09-09): "지금 수정"** — 세 경로 모두 fail-closed로 변경.

**조치**: `src/hosts/pywebview/main.py`의 `request_confirmed_close()`를 다음과 같이
고쳤다.
- JS 쪽 `catch (e) { ... }`가 더 이상 `'yes'`로 처리하지 않고 `'no'`로 처리한다
  (저장 핸들러가 reject하면 닫지 않는다).
- 폴링 타임아웃(10초) 시 더 이상 `window.destroy()`를 호출하지 않는다 — 창을 그대로
  두고 stderr에 로그만 남긴다.
- 바깥 `except Exception`도 더 이상 `window.destroy()`를 호출하지 않는다 — 창을
  그대로 두고 stderr에 로그만 남긴다.

`window.destroy()`는 이제 명시적으로 `'yes'`를 받았을 때 단 한 경로로만 호출된다.
`python -m py_compile`로 구문 확인, `npm run typecheck && npm test`(전 Phase 1~6,
양 호스트) 재통과 확인. 3회 검증 한도는 반대 벤더 CLI 재실행에 적용되는 것이며, 이
수정은 설계 트레이드오프가 아닌 명백한 안전 결함의 직접 교정이라 판단해 추가 CLI
라운드 없이 사람의 승인만으로 반영했다.

### R3-2 (Major) — 진행(progress) 소유권 미구분: D-32의 사각지대인지 별개 결함인지

**재현 조건**: 셸이 `openFolder()`로 진행을 시작 → 그 사이 앱이 자기 진행을 시작 →
셸의 `openFolder()`가 끝나며 무조건 `stopProgress()` 호출 → `progressActive`가 여전히
`true`(앱이 켰으므로)라서 앱의 새 진행이 지워짐.

**위반 조항**: FR-N10b, D-32

**Codex의 독립 판단**: D-32가 명시적으로 받아들인 단점("겹치면 앞엣것이 안 보이고
지나간다")은 메시지가 서로 겹쳐 보이지 않게 되는 것만 다루며, "한 작업의 종료 호출이
다른 작업의 진행을 끝내는 것"까지 허용한다고 보지 않는다는 것이 Codex 3라운드의
결론이다. 즉 D-32 문언 그대로는 이 결함을 사각지대로 인정하지 않는다.

**선택지** (사람 판단 필요):
1. 진행에 소유권/세대 토큰을 추가해 "내가 시작한 진행만 내가 끈다"를 보장한다 —
   `StatusMessageController`의 API 형태 변경(현재 앱 표면의 `startStatusProgress`/
   `stopStatusProgress`가 인자 없음)이 필요해 `WorkbenchAppSurface` 계약이 넓어진다.
2. D-32에 이 사각지대를 명시적으로 추가해 받아들인다(사람이 DECISIONS.md를 고침).
3. 현재 상태로 승인 — 겹치는 진행 호출 자체가 실사용에서 드물다는 전제.

### R3-3 (Major) — pywebview FR-K1 실제 재시작 검증 없음

Electron만 두 프로세스 재시작(`verify-phase6.mjs` 6b절)으로 검증했고, pywebview는
같은 프로세스 내 `editor.clear()` + `restoreLastSession()` 시뮬레이션에 그친다.
pywebview 전용 영속성 회귀는 현재 전체 시험을 통과할 수 있다.

**선택지**: (1) pywebview도 두 프로세스(`python -m ... --phase6-test` 두 번, 같은
`%LOCALAPPDATA%`류 프로필 경로 공유) 방식으로 확장한다 — 별도 작업량 필요.
(2) 현재 상태(코드 경로는 Electron으로 이미 실증됐고 두 호스트가 같은
`localStorage`/`saveLastOpenedFolder` 로직을 공유하므로 호스트별 로직 분기가 없다는
점)를 근거로 승인한다.
