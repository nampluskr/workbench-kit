# BRIEF — workbench-kit

## 1. 배경

이 프로젝트는 새로 시작한다. 하지만 맨땅에서 나오지 않았다. 앞선
`tab-explorer-templates` v0.1은 탐색기 트리·탭·좌우 분할·메뉴·상태 표시줄을 갖춘
공통 껍데기를 pywebview와 Electron 두 갈래로 완성했고, `markdown-viewer`가 그
껍데기를 그대로 물려받아 쓰고 있어 **공통부를 물려받고 소수만 교체하는 방식이 실제로
성립함**이 확인됐다. 이 경험이 workbench-kit의 재료다.

그런데 그 껍데기의 개별 동작은 개발 과정에서 발견된 문제를 그때그때 고치며 자랐다.
탭 이동, 분할 해제, 선택과 포커스처럼 서로 연결된 기능이 하나의 행동 규칙보다 개별
문제 해결을 중심으로 발전했고, 껍데기가 한 파일에 절차적으로 쌓여 상태 전이와 예외가
누적됐다. 완료로 판정했던 일부가 실제로 연결되지 않았거나 검사가 기능의 실체를
확인하지 못한 사례도 뒤늦게 나왔다. 동작이 왜 지금 방식이어야 하는지 견줄 외부 기준도
부족해, 새 요구가 생길 때마다 국소적인 판단이 하나씩 더해졌다.

외부 기준이 없었던 데는 이유가 있다. 그 껍데기는 VS Code OSS가 화면을 어떻게 나누고
무엇을 어디에 두는지를 **모르는 상태에서** 필요한 것을 그때그때 만들어 가며 나왔다.
그런데 다 만들고 보니 그 결과가 VS Code의 구성과 상당 부분 같았다. 즉 사용자가
원하던 것은 처음부터 VS Code가 이미 오래 다듬어 온 구성이었고, 그것을 모른 채
시행착오로 근처까지 간 셈이다.

그렇다면 순서를 바꾸는 편이 낫다. 국소 수정을 계속 쌓는 대신, **처음부터 VS Code를
기준으로 놓고** 거기서 이 용도에 필요한 요소와 구현 방식만 골라 세운다. 앞선
결과물에서 가져올 것은 배치나 구현이 아니라, 사용자가 어떤 요소를 어디에 두고
어떻게 쓰려 했는가라는 의도다. 그래서 이전 결과물을 잇지 않고, 얻은 교훈을 재료로
삼아 새 이름의 프로젝트로 다시 세운다.

## 2. 이번 버전에서 풀고 싶은 문제

무엇보다 이 껍데기는 **작고 단순한 앱을 쉽게 만들 수 있어야 한다.** VS Code처럼 비대한
도구가 아니라, 그 도메인에 꼭 필요한 기능만 담은 앱이 목표다. 이를 위해 공통 UI는 VS
Code OSS의 이미 검증된 구현을 참조해 새로 발명하지 않고, 파일 탐색기 계열과 폴더 탐색기
계열이 같은 일반화된 템플릿을 공유하도록 한다. 그래야 새 앱이 UI 구현과 기능 확인에
노력을 거의 들이지 않고 완성된다.

공통 UI가 어떤 상태를 가지며 사용자 입력에 어떻게 반응하는지를, VS Code가 실제
제품에서 다듬어 온 동작을 기준으로 삼아 하나의 일관된 체계로 정립하고 싶다. 탐색기,
탭, 분할 영역, 선택과 포커스, 키보드 조작은 서로 모순되지 않아야 하고, 같은 상황에서는
같은 결과가 나와야 한다. 탭을 열고 닫거나 옮긴 뒤에도 활성 항목·포커스·보기의 수명이
예측 가능한 규칙을 따라야 한다.

UI 레이아웃은 전면 재작성한다. 큰 틀에서 앞선 `tab-explorer-templates`를 따르지 않고,
VS Code 레이아웃에서 필수 요소와 구현 방식만 참조해 정한다. 앞선 결과물은 VS Code를
모르는 상태에서 시행착오로 만들어졌고 결과적으로 같은 방식에 도달했을 뿐이므로, 거기서
가져올 것은 **사용자가 어떤 요소를 어디에 두고 어떻게 쓰려 했는가**라는 의도뿐이다.
배치·간격·구현 방식은 물려받지 않는다. 다만 색·간격·아이콘의 시각 체계가 앱들이
공유할 하나의 기준으로 정돈된 상태는 유지하고 싶다.

`INTENT.md`가 말하는 재사용이 이 껍데기에서 실제로 성립하기를 원한다. 새 앱이 공통
코어를 손대지 않고 갈아끼우는 자리만으로 완성되고, 두 갈래(pywebview·Electron)에서
같은 사용자 동작이 같은 결과를 내야 한다. 검사가 풍부해도 검사 통과만으로 실제 기능
연결과 사용자 동작이 검증되었다고 간주하지 않는 상태를 원한다.

## 3. 하지 않을 것

- 검증용 세 앱(마크다운 뷰어·파일 커맨터·멀티터미널) 중 어느 것의 도메인 기능도
  구현하지 않는다. 이번에 만드는 것은 그것들이 꽂힐 자리다.
- VS Code 전체를 복제하거나 범용 코드 편집기를 만들지 않는다.
- VS Code의 확장 호환성, 소스 제어, 검색, 디버깅, 통합 터미널 등 이 템플릿의 목적을
  벗어난 제품 기능을 넣지 않는다.
- 시각 체계를 새 브랜드로 전면 재정의하지 않는다. 겉보기는 처음부터 다시 구성하되,
  세 색상 테마가 앱들이 공유하는 하나의 기준으로 남는다. 아이콘은 직접 그리지 않고
  아이콘 라이브러리(UI 아이콘·파일 종류 아이콘)를 써서 세 색 테마에 맞춰 보이게 한다.
- 설치형 라이브러리나 패키지로 배포하지 않는다. 복사해서 쓰는 템플릿으로 둔다.
- 모바일·클라우드 배포를 고려하지 않는다.
- pywebview와 Electron 중 하나를 버리거나 하나로 합치지 않는다.

## 4. 완료 조건

- 탐색기·탭·분할 영역·선택과 포커스·키보드 및 마우스 조작 각각에 대해, 참고한
  VS Code의 동작과 이 템플릿이 채택한 동작을 사람이 대조할 수 있는 기준 문서가 있다.
  기준과 다르게 둔 동작은 그 차이가 의도임이 기록되어 있다.
- **사용자 시나리오 목록**이 있다. 정상 동작뿐 아니라 빈 상태, 중복 열기, 탭 닫기,
  칸 닫기, 칸 사이 이동, 저장하지 않은 채 닫기, 실패 상황이 그 안에 들어 있고,
  항목마다 정해진 결과가 하나씩 적혀 있다. **그 목록의 모든 항목이 적힌 대로 나온다.**
  (그 목록은 `SPEC.md` 1절이다. `refs/scenarios.md`는 그 재료였던 초안이다.)
- 시험이 등록한 임의의 리소스 종류 하나가 공통 코어 수정 0줄로 탭에서 열린다.
- 어떤 탭을 다른 탭으로 전환했다 돌아오거나 반대쪽 패널로 옮겨도 보기 인스턴스가
  다시 만들어지지 않고, 탭을 닫을 때만 폐기된다.
- 파일 프리셋과 폴더 프리셋이 공통 코어 수정 0줄로 각각 아래를 만족한다. 탭 안에
  무엇을 그리는지는 앱의 몫이므로 여기서 판정하지 않는다.
  - 파일 프리셋: 트리에 파일이 보이고, 행을 고르면 **그 파일을 대상으로 하는 보기**가
    탭에 열린다.
  - 폴더 프리셋: 트리에 폴더가 보이고, 행을 고르면 **그 폴더를 대상으로 하는 보기**가
    탭에 열린다.
- 위 항목이 pywebview와 Electron에서 같은 결과로 확인된다. **`SPEC.md` 1절의 모든
  항목을 두 갈래에서 각각 확인했고, 결과가 다른 항목이 하나도 없다.**
- 사용자 시나리오를 확인하는 동작 검사가 전건 통과한다. 구현 세부를 확인하는 검사와
  사용자 행동을 확인하는 검사가 문서에서 구분되어 있다.
- 껍데기가 반입한 것들의 라이선스 본문과 저작자 표시가 템플릿 안에 들어 있고, 복사한
  사람이 따로 챙길 것이 없다.
