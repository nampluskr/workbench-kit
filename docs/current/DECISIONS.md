# DECISIONS — workbench-kit

## D-1. 무빌드 원칙을 폐기하고 빌드를 전제로 한다

**선택**

이전 프로젝트(`tab-explorer-templates` · `markdown-viewer`)가 지켰던 "번들러 없이
그대로 로드하는 무빌드" 원칙을 이번 프로젝트에서는 따르지 않는다. 빌드 단계를 두고,
코드가 바뀌면 무조건 재빌드하는 것을 기본으로 한다.

**근거**

이 프로젝트의 원칙은 "무빌드"가 아니라 **"최소 구현"**이다. 필요한 기능을 제대로
구현하고 빌드해서 쓰는 편이, 무빌드 제약에 맞추느라 기능을 우회하거나 좁히는 것보다
목적에 맞다. 빌드를 전제해야 monaco-editor · codicons 같은 빌드형 라이브러리를 쓸 수
있다(D-2). 이것이 이전 프로젝트에서 이번 프로젝트로 넘어오며 바뀐 지점이다.

**배제한 대안**

- **무빌드 원칙을 유지한다(이전 프로젝트 방식).** 번들러 없이 로드되는 배포본만 써야
  해서 쓸 수 있는 라이브러리와 구현 방식이 좁아진다. 최소 구현을 오히려 방해하므로
  배제한다.

---

## D-2. VS Code OSS는 fork하지 않고 참고만 하며, bottom-up으로 필요한 기능만 구현한다

**선택**

VS Code OSS 저장소를 fork해 불필요한 것을 걷어내는 방식(top-down)을 쓰지 않는다.
VS Code OSS는 동작과 구현을 참고하는 자료로만 보고, 이 프로젝트에 필요한 기능만
밑에서부터 새로 구현한다(bottom-up). 다만 monaco-editor · codicons처럼 독립적으로
배포되어 빌드해 쓸 수 있는 라이브러리는 그대로 가져다 쓴다.

**근거**

제1원칙이 최소 구현이다. VS Code 전체를 안고 축소하면 쓰지 않는 방대한 코드와 그
상태·예외를 계속 떠안게 되어 최소·단순과 정반대가 된다. 필요한 기능만 참고해 새로
짜면 껍데기가 작게 유지되고, 왜 그 동작이어야 하는지를 VS Code라는 외부 기준과
대조할 수 있다(BRIEF의 기준 문서). 반대로 이미 검증된 라이브러리를 다시 만드는 것도
최소 구현에 어긋나므로, 그런 것은 반입한다.

**배제한 대안**

- **VS Code OSS를 fork해 축소한다(top-down).** 방대한 미사용 코드와 그 유지 부담을
  그대로 안게 되어 최소 구현 원칙과 어긋나므로 배제한다.
- **라이브러리도 쓰지 않고 전부 자체 구현한다.** monaco-editor · codicons처럼 이미 잘
  만들어진 것을 다시 만드는 비용이 크고, 이 역시 최소 구현에 어긋나므로 배제한다.

## D-3. 아이콘은 직접 그리지 않고 아이콘 라이브러리를 쓴다

**선택**

UI/제품 아이콘(툴바·펼침 화살표·창 버튼 등)은 **codicons**를 반입해 쓴다. VS Code가
실제로 쓰는 그 아이콘 폰트이며, `@vscode/codicons`로 배포된다. 파일 종류 아이콘은
D-17에서 정한다. 아이콘을 직접 그리거나 색 테마별로 따로 그리지 않는다. codicons는
단색 글꼴이라 세 색 테마에 맞춰 색만 바뀐다.

앞선 `tab-explorer-templates`는 UI 아이콘을 직접 그린 한 벌(`icons.svg`)로 갖고
있었다. 이번에는 그것을 쓰지 않고 codicons로 바꾼다.

**라이선스** — codicons는 이중 라이선스다. 저장소의 **코드는 MIT**지만 **아이콘
자체는 CC BY 4.0**이므로 저작자 표시가 필요하다. 반입할 때 표시 문구를 함께 넣는다.

**근거**

최소 구현 원칙(D-1 · D-2). 빌드를 전제하므로 아이콘 라이브러리를 그대로 넣을 수 있고,
이미 검증된 아이콘 세트를 다시 만들 이유가 없다.

**배제한 대안**

- **아이콘을 직접 그리고 색 테마마다 따로 그린다.** 만들고 유지하는 비용이 크고 최소
  구현에 어긋나므로 배제한다. 단색 UI 아이콘은 색만 바꿔 쓴다.

**바로잡음** — 이 항목은 처음에 "이전 프로젝트의 '세 아이콘 테마'"를 배제 대상으로
적었으나 사실이 아니었다. 앞선 `tab-explorer-templates`의 세 테마는 직접 그린 세
벌이 아니라 **사용자가 고를 수 있는 세 가지 파일 아이콘 스타일**이었고, 그중 둘은
이미 라이브러리다(D-17).

## D-4. 터미널 같은 살아 있는 보기는 앱이 제공하고, 껍데기는 탭과 호스트 브릿지만 준다

**선택**

폴더 탐색기의 터미널처럼 살아 있는 세션 보기는 껍데기가 만들지 않는다. 껍데기는 그런
보기를 담을 탭 · 수명 관리 · 호스트 브릿지만 제공하고, 터미널 로직(xterm.js · PTY 등)과
"폴더 경로 → 그 경로의 터미널 열기" 매핑은 멀티터미널 앱(폴더 프리셋) 안에 둔다.

**근거**

"껍데기는 리소스 종류를 모른다"(INTENT). 터미널은 대상의 한 종류일 뿐이고, 껍데기가
터미널을 알면 이 원칙이 깨져 다음 앱이 같은 껍데기를 못 쓴다. VS Code의 "통합
터미널"(하단 Panel)을 만들지 않는다는 것과도 일치한다. 껍데기가 증명할 것은 "살아
있는 비-파일 보기를 탭이 담고 수명 동안 유지한다"까지다.

**배제한 대안**

- **껍데기가 통합 터미널을 기본 기능으로 넣는다.** 리소스 종류를 아는 코드가 껍데기로
  새고 VS Code식 하단 Panel을 재현하게 되므로 배제한다.

---

## D-5. 탭은 사용자가 추가할 때만 늘어난다 — 탐색기 선택은 현재 탭에서 연다

**선택**

- 탐색기에서 항목을 고르면 **현재 탭 영역의 활성 탭에서 열린다.** 탭 개수는 늘지
  않는다. 껍데기가 스스로 탭을 만드는 경우는 없다.
- 고른 항목이 **이미 다른 탭에 열려 있으면 그 탭으로 이동한다.** 파일과 폴더에 같은
  규칙이 적용된다.
- **새 탭은 사용자가 명시적으로 추가할 때만 생긴다.**
- 사용자가 방금 추가한 탭에서 이미 열려 있는 항목을 고르면, 이동하지 않고 **그 탭에
  새로 연다.** 즉 중복 검사는 탐색기 선택에만 걸리고, 사용자가 만든 탭에는 걸리지
  않는다.

**근거**

탭이 저절로 불어나면 사용자가 탭 줄을 정리하는 데 노력을 쓴다. 제1원칙인 최소·단순에
어긋난다. 고를 때마다 현재 탭에서 열리면 탭 줄은 사용자가 의도한 만큼만 길어진다.

중복 이동 규칙이 파일과 폴더에 똑같이 적용되므로 껍데기가 리소스 종류를 알 필요가
없다(INTENT 3절 "껍데기는 리소스 종류를 모른다").

사용자가 탭을 추가하는 행위 자체가 "하나 더 원한다"는 명시적 의사다. 그래서 그
자리에서는 중복 검사를 하지 않는다. 멀티터미널이 한 폴더에 터미널을 여러 개 두는
것이 이 규칙 하나로 성립하며, 껍데기에 터미널이나 세션을 아는 코드가 들어가지
않는다(D-4).

**배제한 대안**

- **탐색기에서 고를 때마다 새 탭을 연다.** 사용자가 조작하지 않았는데 탭이 불어나고,
  그것을 정리하는 부담이 사용자에게 넘어간다. 배제한다.
- **중복이면 언제나 기존 탭으로 이동한다(사용자가 추가한 탭에서도).** 같은 폴더에
  터미널 둘을 띄울 수단이 사라진다. 앱이 그것을 우회하려면 껍데기 밖에서 탭을 직접
  조작해야 하므로 배제한다.
- **대상 종류에 따라 이동과 새로 열기를 가른다**(파일은 이동, 세션은 새로). 껍데기가
  리소스 종류를 알게 되어 INTENT 3절과 어긋나므로 배제한다.
- **VS Code의 미리보기 탭·고정 탭을 도입한다.** VS Code는 한 번 고르면 미리보기 탭,
  두 번이면 고정 탭으로 두어 탭이 불어나는 것을 막는다. 위 규칙은 "탭은 사용자가
  추가할 때만 생긴다" 하나로 같은 문제를 풀며, 탭에 두 가지 상태를 더하지 않는다.
  최소·단순에 비추어 배제한다.

## D-6. 이번 버전에서 두 갈래를 함께 만든다 — 검증 앱이 한쪽에만 있어도 그렇다

**선택**

v0.1에서 pywebview 갈래와 Electron 갈래를 둘 다 만든다. 먼저 착수할 세 앱(마크다운
뷰어·파일 커맨터·멀티터미널)이 전부 Electron 쪽이고 pywebview 갈래를 쓰는 앱이 이번에
없더라도, 껍데기는 두 갈래로 낸다.

**근거**

이 껍데기 위에 올릴 앱은 두 종류가 다 나온다. 수치해석·시뮬레이션·머신러닝·딥러닝처럼
계산이 파이썬에 있는 작업이 계속 있고, 그런 앱은 화면을 파이썬 쪽에서 띄워야 하므로
pywebview 갈래를 요구한다(INTENT 5절). 지금 그 앱을 안 만든다는 것과 그 갈래가
필요 없다는 것은 다르다.

공통부를 한 갈래로만 완성하면 나중에 다른 갈래를 붙일 때 공통부를 다시 헤집게 된다.
그것은 "새 앱마다 드는 노력을 최소화한다"는 목적과 정반대다. 두 갈래를 처음부터
같이 두어야 갈래 차이가 공통 코어 밖으로 밀려난다.

검증에는 도메인 앱이 필요하지 않다. 완료 조건은 껍데기 자체의 동작으로 판정되며,
리소스 종류도 시험이 등록한 것으로 확인한다(BRIEF 완료 조건). 따라서 pywebview
갈래에 도메인 앱이 없어도 동등성을 판정할 수 있다.

**배제한 대안**

- **v0.1은 Electron만 만들고 pywebview는 다음 버전으로 미룬다.** 세 앱을 빨리 쓰는
  데는 유리하지만, 두 번째 갈래를 붙일 때 이미 완성된 공통부를 뒤늦게 갈라야 한다.
  갈래 차이가 공통 코어로 스며들 위험이 가장 큰 선택이라 배제한다.
- **pywebview 갈래를 아예 버리고 Electron 하나로 간다.** 파이썬 계산이 필요한 앱을
  이 껍데기 위에 올릴 수 없게 되어 INTENT 5절과 어긋나므로 배제한다.

## D-7. 화면은 다섯 조각이다 — 프레임리스로 가되 세로 띠는 남기고 가로 메뉴 줄만 없앤다

**선택**

창을 프레임리스로 띄우고, 화면을 아래 다섯 조각으로 구성한다.

1. **상단 바** — 운영체제가 그려 주던 제목 줄을 우리가 대신 그린다. 왼쪽에 메뉴를
   여는 햄버거 버튼(`≡`), 가운데에 창 제목, 오른쪽에 최소화·최대화·닫기.
   창 끌기와 크기 조절도 여기서 직접 처리한다.
2. **맨 왼쪽 세로 띠(활동 표시줄)** — 자주 쓰는 명령을 아이콘으로 세워 둔다. 무엇을
   놓을지는 D-11에서 정한다.
3. **왼쪽 탐색기** — VS Code의 탐색기 형태를 그대로 따른다. 제목줄과 뷰 액션 아이콘,
   그 아래 트리(D-9).
4. **오른쪽 탭 영역** — 탭 줄과 보기(D-8 · D-10).
5. **하단 바** — 지금 대상의 경로와 앱 정보.

가로로 늘어선 **메뉴 줄은 별도 줄로 두지 않는다.** 상단 바의 햄버거 버튼을 누르면
VS Code의 컴팩트 메뉴처럼 File·View·Help의 내용이 펼쳐진다.

**근거**

프레임리스를 고른 이유는 공간 최적화다. 다만 아끼는 방식이 방향마다 다르다.

*세로 방향은 아낀다.* 창틀과 가로 메뉴 줄은 각각 한 줄씩을 상시로 차지하면서 담는
정보가 거의 없다. 메뉴는 눌러야 볼 내용이지 늘 보고 있을 내용이 아니므로, 햄버거
버튼 하나로 접으면 높이를 통째로 돌려받는다.

*가로 방향의 세로 띠는 남긴다.* 이 자리는 접기 대상이 아니라 **자주 쓰는 명령을 한
번에 누르는 자리**다. 메뉴 안에 들어가면 두 번 눌러야 하는 것을 한 번에 눌 수 있게
하는 값어치가 폭 40~50px보다 크다. 메뉴와 세로 띠는 같은 것을 두 곳에 두는 중복이
아니라 **역할이 다르다** — 메뉴는 전부를 담고, 세로 띠는 자주 쓰는 것만 담는다.

VS Code의 세로 띠는 사이드바에 어떤 뷰를 띄울지 고르는 자리지만, 이 껍데기는 뷰가
탐색기 하나뿐이라 그 용도가 없다. 그래서 **용도를 바꿔 쓴다.** 생김새는 VS Code를
따르되 담기는 것이 다르다는 점을 D-11에 적어 둔다.

탐색기를 VS Code 형태 그대로 두는 것은 이 부분이 사용자가 가장 익숙하고, 새로
발명할 이유가 없는 자리이기 때문이다(INTENT 6절).

**배제한 대안**

- **세로 띠를 없애고 그 기능을 전부 상단 바와 단축키로 옮긴다.** 폭은 아끼지만 자주
  쓰는 명령이 메뉴 안으로 들어가 조작이 한 단계 늘어난다. 상단 바는 창 버튼과 제목이
  이미 차지하고 있어 아이콘을 여러 개 놓을 자리도 아니다. 배제한다.
- **File/View/Help를 가로 메뉴 줄로 상시 노출한다.** 프레임리스로 아낀 높이를 그대로
  반납하는데, 메뉴는 늘 보고 있을 내용이 아니다. 배제한다.
- **운영체제 창틀을 그대로 쓴다(프레임리스가 아니다).** 아무 정보도 담지 않는 제목
  줄이 한 줄을 차지한다. 배제한다.
- **하단 바도 없앤다.** 지금 보고 있는 대상의 경로는 실제로 쓰이고 높이가 한 줄이라
  손해가 작다. 배제한다.

## D-8. 칸은 가로·세로 모두 나눌 수 있다 — 2차원 배치는 dockview가 관리한다

**선택**

오른쪽 탭 영역을 여러 칸으로 나눌 수 있게 한다. **VS Code와 같이 가로(좌우)·세로(위아래)
모두 나눌 수 있고**, 칸 개수에 제한을 두지 않는다. 칸마다 자기 탭 줄을 가진다.

배치가 2차원 격자가 되면서 따라오는 것들 — 칸을 없앨 때 남은 칸이 자리를 나눠 갖는
것, 탭을 옮길 때 목표 칸을 정하는 것, 경계를 끌어 크기를 조절하는 것, 배치를 저장하고
복원하는 것 — 은 **직접 짜지 않고 dockview에 맡긴다(D-24).**

**근거**

멀티터미널이 한 폴더에서 AI 에이전트를 여러 개 돌리는 용도이므로, 셋 이상을 나란히
보는 일이 실제로 생긴다. 칸이 하나뿐이면 탭 전환으로만 오갈 수 있어 이 용도가
성립하지 않는다.

처음에는 세로 분할을 빼서 칸 배치를 **1차원 목록**으로 유지하려 했다. 2차원이 되면
"칸을 없앨 때 남은 칸을 어디에 붙이나", "탭을 옮길 때 목표 칸이 어디인가" 같은
규칙이 급격히 늘고, 앞선 프로젝트가 무너진 자리가 정확히 그 근처(분할 해제·탭
이동)이기 때문이다(BRIEF 1절).

그 위험은 그대로다. 다만 **그 규칙을 우리가 짜지 않기로 하면서** 판단이 바뀌었다.
dockview가 2차원 격자 배치를 이미 구현하고 있고 그 코드가 VS Code에서 나왔다(D-24).
검증된 구현을 가져다 쓴다면, 1차원으로 억지로 좁혀 VS Code와 다르게 동작하게 만들
이유가 없다. 이 껍데기의 기준은 "VS Code 방식을 따른다"이고(INTENT 6절), 분할도
그 방식을 따른다. 이 껍데기가 VS Code와 의도적으로 다른 것은 Zen 모드 하나뿐이다(D-12).

**배제한 대안**

- **가로로만 나누고 세로 분할은 두지 않는다(1차원 목록).** 규칙이 짧게 유지되는
  이점이 있으나, 그 규칙을 dockview가 이미 갖고 있어 우리가 떠안는 몫이 아니다.
  1차원으로 좁히면 VS Code와 다르게 동작하고 divergence가 하나 더 생긴다. 배제한다.
- **칸을 하나로 두고 탭 전환만 지원한다.** 가장 단순하지만 나란히 비교하는 용도와
  멀티터미널이 성립하지 않으므로 배제한다.
- **가로 두 칸까지만 허용한다(앞선 프로젝트 방식).** 터미널 셋을 나란히 두지 못한다.
  개수 제한이 규칙을 단순하게 만들어 주지도 않으므로 배제한다.
- **2차원 배치 규칙을 직접 짠다.** 앞선 프로젝트가 실패한 지점이라 배제한다(D-24).

## D-9. 탐색기 트리는 VS Code의 외형과 키보드 조작을 그대로 따른다

**선택**

왼쪽 탐색기의 **생김새와 키보드 동작을 VS Code와 같게** 만든다.

*외형* — 폴더 앞 펼침 화살표(`▸` 접힘 / `▾` 펼침), 확장자별 파일 종류 아이콘,
깊이를 나타내는 들여쓰기 안내선, 포커스 항목과 선택 항목의 구분 표시. 뷰 제목줄
오른쪽의 액션 아이콘(새로고침·모두 접기 등 — **어느 액션을 누가 하는지는 D-30**).

*키보드* — VS Code의 목록·트리 기본 키를 그대로 채택한다.

| 키 | 동작 | VS Code 명령 |
| --- | --- | --- |
| `↑` `↓` | 위아래 이동 | `list.focusUp` · `list.focusDown` |
| `→` | 펼치기 (이미 펼쳐졌으면 첫 자식으로) | `list.expand` |
| `←` | 접기 (이미 접혔으면 부모로) | `list.collapse` |
| `Ctrl+←` | 모두 접기 | `list.collapseAll` |
| `Space` | 펼침/접힘 뒤집기 | `list.toggleExpand` |
| `Enter` | 열기 | `list.select` |
| `Home` `End` | 처음 / 끝으로 | `list.focusFirst` · `list.focusLast` |
| `PageUp` `PageDown` | 한 화면씩 | `list.focusPageUp` · `list.focusPageDown` |
| `Ctrl+↑` `Ctrl+↓` | 포커스는 두고 스크롤만 | `list.scrollUp` · `list.scrollDown` |
| `Shift+↑` `Shift+↓` | 선택 범위 넓히기 | `list.expandSelectionUp` · `...Down` |
| `Ctrl+A` | 전체 선택 | `list.selectAll` |
| `Ctrl+Shift+Enter` | 지금 항목 선택 토글 | `list.toggleSelection` |
| `Escape` | 선택 해제 | `list.clear` |
| `F3` · `Ctrl+Alt+F` | 트리 안에서 찾기 | `list.find` |
| `Ctrl+Enter` | 옆 칸에 열기 | `explorer.openToSide` |

마우스의 `Ctrl+클릭` · `Shift+클릭` 다중 선택도 함께 지원한다.

**넣지 않는 것** — `Alt+↑/↓/Home/End`(`list.focusAny*`), `Ctrl+K Ctrl+I`(항목 설명
말풍선), `Shift+Alt+F`(폴더 안 검색). 앞의 둘은 쓰임이 드물고, 마지막은 검색 기능
자체가 범위 밖이다(BRIEF 3절).

**근거**

탐색기는 사용자가 가장 익숙한 부분이고, 여기서 다르게 만들 이유가 없다. 새로
발명하지 않는다는 INTENT 6절이 가장 직접적으로 적용되는 자리다. 키를 하나라도 다르게
두면 "왜 여기만 다른가"를 매번 판단해야 하는데, 그 판단 비용이 얻는 것보다 크다.

다중 선택은 취향이 아니라 요구다. **파일 커맨터**는 여러 파일을 골라 한 번에 다루는
도구이므로 다중 선택 없이는 성립하지 않는다.

이 트리는 VS Code가 따로 배포하지 않아 가져다 쓸 수 없다. 동작만 참고해 직접 짠다.
위 표가 그 구현의 판정 기준이 된다.

**배제한 대안**

- **최소 키만 둔다(위아래·펼침·열기 정도).** 익숙한 키가 안 먹는 순간 사용자는 이
  도구가 어디까지 되는지 매번 시험해야 한다. 익숙함을 그대로 물려받는다는 목적과
  어긋나므로 배제한다.
- **다중 선택을 빼고 한 번에 하나만 고르게 한다.** 파일 커맨터가 성립하지 않으므로
  배제한다.
- **트리를 다른 라이브러리로 가져온다.** VS Code 트리는 별도 배포되지 않고, 다른
  라이브러리는 위 키 조합과 외형이 달라 "동일하게"를 만족시키지 못한다. 배제한다.

**범위에 대한 메모** — 위 목록 중 `list.find`(트리 안에서 찾기)가 가장 비싸다.
범위를 줄여야 할 상황이 오면 여기서부터 덜어낸다.

## D-10. 탭 영역은 VS Code 방식을 따른다 — 단 탭이 늘어나는 규칙은 D-5가 우선한다

**선택**

오른쪽 탭 영역의 생김새와 조작을 VS Code와 같게 만든다. 칸마다 탭 줄이 있고, 활성
탭이 구분되며, 탭에 닫기 버튼이 있고, 탭을 끌어서 같은 줄에서 순서를 바꾸거나 다른
칸으로 옮길 수 있다. 칸은 **둘 이상** 만들 수 있다(D-8).

다만 **탭이 언제 새로 생기는가는 D-5를 따른다.** 탐색기에서 고르면 현재 탭에서
열리고, 이미 열려 있으면 그 탭으로 가며, 새 탭은 사용자가 추가할 때만 생긴다.
VS Code의 미리보기 탭·고정 탭은 두지 않는다.

**근거**

탭 줄의 생김새와 끌어 옮기기는 익숙한 대로 두는 것이 맞다. 그러나 "무엇을 열면 탭이
몇 개가 되는가"는 이 도구의 성격이 VS Code와 다른 지점이다 — VS Code는 편집기라 파일이
계속 쌓이지만, 이 껍데기 위의 앱들은 한 번에 보는 대상이 적고 터미널처럼 오래 사는
탭이 많다. 그래서 그 규칙만 D-5로 갈라 두었고, 그 판단을 여기서 뒤집지 않는다.

**배제한 대안**

- **VS Code의 탭 생성 규칙까지 그대로 따른다.** D-5를 폐기하게 되고, 미리보기 탭·고정
  탭이라는 두 가지 탭 상태가 다시 들어온다. 최소·단순에 어긋나므로 배제한다.
- **탭을 끌어 옮길 수 없게 한다.** 칸을 나눠 놓고 탭을 옮길 수 없으면 칸을 나눈 뜻이
  절반으로 줄고, 터미널처럼 닫으면 죽는 탭은 우회할 방법도 없다. 배제한다.

## D-11. 세로 띠는 뷰를 고르는 자리가 아니라 자주 쓰는 명령을 담는 자리다

**선택**

맨 왼쪽 세로 띠(활동 표시줄)를 둔다. 다만 VS Code처럼 "사이드바에 어떤 뷰를 띄울지
고르는" 용도로 쓰지 않는다. 이 껍데기는 뷰가 탐색기 하나뿐이라 고를 대상이 없다.
대신 **자주 쓰는 명령을 아이콘 하나로 누르는 자리**로 쓴다.

지금 정해진 항목은 위쪽부터 탐색기 접기/펴기, 상단 바 감추기/보이기, 하단 바
감추기/보이기(D-14), 좌우 스플릿, 상하 스플릿(D-13), Zen 모드(D-12)다. 아래쪽에 테마
바꾸기를 둔다(VS Code가 설정을 띠 아래쪽에 두는 자리와 같다). **칸 삭제·칸 합치기
아이콘은 두지 않는다** — 칸은 탭을 모두 비우면 사라지고(D-26), 합치기는 VS Code에
있으나 이 껍데기는 노출하지 않는다.

메뉴와 겹치는 것은 중복이 아니다. **메뉴는 전부를 담고 세로 띠는 자주 쓰는 것만
담는다.** 어떤 명령이 자주 쓰이는지는 쓰면서 바뀔 수 있으므로 항목은 늘거나 줄 수
있다. 늘고 주는 것이 껍데기 코드를 고치는 일이 되지 않도록, 띠에 놓을 항목은
갈아끼우는 자리에서 정한다.

**근거**

메뉴 안에 들어가면 두 번 눌러야 하는 것을 한 번에 누를 수 있다. 탐색기 접기처럼
하루에 수십 번 누르는 것은 그 차이가 크다.

띠의 항목을 껍데기가 고정하면 앱마다 자주 쓰는 명령이 다른데도 같은 아이콘을 이고
가야 한다. "껍데기는 리소스 종류를 모른다"(INTENT 3절)와 같은 이유로, 무엇을 놓을지는
앱이 정하게 한다. 껍데기는 띠와 그 자리만 준다.

**배제한 대안**

- **VS Code처럼 뷰 전환 버튼을 놓는다.** 뷰가 탐색기 하나뿐이라 전환할 대상이 없다.
  배제한다.
- **띠의 항목을 껍데기가 고정한다.** 앱마다 자주 쓰는 명령이 다르므로 배제한다.
- **띠를 두지 않고 전부 메뉴로 보낸다.** D-7에서 배제했다.
- **칸 삭제·칸 합치기 아이콘을 둔다.** 칸은 탭을 모두 닫으면 사라지므로(D-26) 삭제
  아이콘은 중복이다. 합치기는 어느 칸과 합치나·탭 순서는 어떻게 되나 하는 규칙을
  새로 만든다. 둘 다 배제한다.

## D-12. 탐색기 접기와 Zen 모드를 둔다 — Zen은 전체화면이 아니라 탭과 보기만 남긴다

**선택**

**탐색기 접기** — 왼쪽 탐색기를 접었다 폈다 한다. 세로 띠의 첫 아이콘과 단축키로
누른다. 접으면 탐색기 자리가 사라지고 그만큼 탭 영역이 넓어진다. 세로 띠는 남는다.

**Zen 모드** — 창을 전체화면으로 만들지 않는다. 대신 **상단 바 · 세로 띠 · 탐색기 ·
그 사이 경계 · 하단 바를 모두 감추고, 탭 줄과 보기만 남긴다.** `F11`로 켜고 끄며
`Escape`로도 빠져나온다.

**근거**

앞선 `tab-explorer-templates`가 이미 이 방식이었고(`shell/shell.css`의 zen 규칙이
메뉴 줄·활동 표시줄·사이드바·스플리터·상태 표시줄을 감춘다), 실제로 쓰면서 불편이
없었다. 새로 발명할 이유가 없다.

전체화면으로 바꾸지 않는 것이 핵심이다. 전체화면은 운영체제 창 상태를 건드려서
빠져나오는 방법이 갈래마다 달라지고, 여러 창을 나란히 두고 쓰는 작업과 맞지 않는다.
이 도구의 Zen은 "창 크기는 그대로 두고 군더더기만 없앤다"이다.

탭 줄을 남기는 것도 중요하다. 멀티터미널에서 탭 줄까지 감추면 터미널 사이를 오갈
방법이 단축키밖에 없어진다.

**배제한 대안**

- **VS Code처럼 전체화면으로 전환하고 탭 줄까지 감춘다.** 창 상태를 건드리는 것이
  두 갈래에서 다르게 동작할 여지를 만들고, 탭 줄이 없으면 멀티터미널에서 오갈 수단이
  사라진다. 배제한다.
- **탐색기 접기만 두고 Zen 모드는 두지 않는다.** 접어도 세로 띠·상단 바·하단 바가
  남아 보기에 온전히 집중할 수 없다. 배제한다.
- **Zen에서 탐색기만 감춘다.** 그것은 탐색기 접기와 같아져 별도 기능일 이유가 없다.
  배제한다.

## D-13. 새 칸은 오른쪽 또는 아래쪽에 생긴다 — 방향마다 아이콘이 있다

**선택**

새 칸을 만드는 방향은 **오른쪽과 아래쪽 둘**이다. VS Code의 좌우·상하 분할과 같되,
이 껍데기는 이 두 방향만 노출한다. 만든 뒤에는 칸을 끌어서 자리를 바꿀 수 있다
(dockview — D-24).

부르는 자리는 넷이다. 전부 VS Code에 있는 방식이다.

1. **각 칸 탭 줄 오른쪽 끝의 두 아이콘** — 좌우 스플릿 `[|]` 정사각형 안 세로줄
   (codicon `split-horizontal`), 상하 스플릿 `[--]` 정사각형 안 가로줄
   (codicon `split-vertical`, codicons에 없으면 `split-horizontal`을 90° 돌려 쓴다).
   그 오른쪽에 새 탭 `+`(D-15).
2. **세로 띠**(D-11) — 같은 두 아이콘.
3. **View 메뉴**(D-23) — "좌우 스플릿", "상하 스플릿".
4. **탭을 편집기 가장자리로 끌기** — 오른쪽 가장자리에 떨구면 오른쪽에, 아래쪽
   가장자리에 떨구면 아래쪽에 새 칸이 생긴다.

```
┌────────────────────────────────────────────┐
│  tab   tab   tab                 [|] [-] +  │
└────────────────────────────────────────────┘
   [|] 좌우 스플릿 → 오른쪽에 새 칸
   [-] 상하 스플릿 → 아래쪽에 새 칸
   +   새 탭 (D-15)
```

**탭 제목 우클릭 메뉴에는 칸 명령을 넣지 않는다**(D-13 배제한 대안 · D-22).

탭에는 닫기 버튼이 있다(D-10). 칸을 명시적으로 닫는 길은 없다 — 칸의 탭이 모두
닫히면 그 칸이 사라지고, 마지막 한 칸은 빈 채로 남는다(D-26).

**근거**

VS Code 동작을 기본으로 삼는다(이 껍데기의 divergence는 Zen 모드 하나뿐 — D-12).
VS Code는 좌우·상하로 나누고, 각 편집기 그룹 오른쪽 위에 분할 아이콘을 두며, 탭을
가장자리로 끌어 새 그룹을 만든다. 그대로 따른다.

방향을 오른쪽·아래쪽 둘로만 좁힌 것은 왼쪽·위쪽 분할이 결국 같은 배치를 만드는
중복 조작이기 때문이다. 끌어서 자리를 바꿀 수 있으므로(dockview) 만들 때 네 방향을
다 줄 필요가 없다.

아이콘을 방향마다 하나씩 둔 것은 "지금 어느 방향으로 나뉘는가"가 누르기 전에 보여야
하기 때문이다. VS Code처럼 한 아이콘에 `Alt`를 섞어 직교 방향을 내는 방식은 숨은
조작이라 두지 않는다.

`[|]`·`[--]`와 `+`를 나눈 것은 뜻이 섞이지 않게 하기 위해서다. `+`는 브라우저에서
"새 탭"으로 굳은 기호라 칸에 쓰면 새 탭 버튼이 갈 자리가 없어진다.

**배제한 대안**

- **오른쪽 한 방향으로만, 방향 선택 없이.** 처음에 이렇게 정했다(1차원 배치 — 옛 D-8).
  D-8이 2차원 배치를 dockview에 맡기기로 바뀌면서 근거가 사라졌다. VS Code와 다르게
  동작하고, 아래쪽으로 나란히 보고 싶을 때 길이 없다. 배제한다.
- **네 방향(좌·우·상·하) 아이콘을 모두 둔다.** 왼쪽·위쪽은 끌어서 자리를 바꾸면
  같은 결과라 아이콘이 하는 일이 겹친다. 배제한다.
- **한 아이콘 + `Alt`로 직교 방향(VS Code 방식).** 누르기 전에 방향이 안 보이는 숨은
  조작이다. 배제한다.
- **탭 제목 우클릭 메뉴에도 칸 명령을 넣는다.** 같은 명령으로 가는 길이 넷을 넘고,
  우클릭 메뉴는 그 탭 자체에 대한 명령을 담는 자리로 남기는 편이 낫다. 배제한다.
- **탭을 끌어 칸을 만드는 것은 두지 않는다.** VS Code에 있고 dockview가 이미 지원한다.
  굳이 뺄 이유가 없다. 배제한다.
- **칸을 끌어 놓기로 만든다(탭을 가장자리로 끌면 칸이 생긴다).** 발견하기 어렵고
  실수로 칸이 생기기 쉽다. 끌어 놓기는 이미 있는 것을 옮기는 데만 쓴다. 배제한다.

## D-14. 상단 바와 하단 바를 각각 따로 감출 수 있다

**선택**

세로 띠의 기본 항목에 둘을 더한다 — **상단 바 감추기/보이기**, **하단 바
감추기/보이기**. 각각 독립이며 서로에게 영향을 주지 않는다.

Zen 모드(D-12)와 별개다. Zen은 한 번에 전부 감추고, 이 둘은 하나씩 감춘다.

**근거**

Zen은 전부 아니면 전무다. "탐색기는 그대로 두고 아래 줄만 없애고 싶다"거나 "제목
줄만 없애 세로를 한 줄 더 벌고 싶다" 같은 중간 상태가 실제로 자주 필요한데, Zen으로는
그것을 만들 수 없다.

**배제한 대안**

- **Zen 모드 하나로 충분하다고 본다.** 중간 상태를 만들 수 없어 배제한다.
- **감추기 설정을 메뉴에만 둔다.** 상황에 따라 자주 바꾸는 것이라 한 번에 눌러야
  한다. 배제한다.

**세로 띠는 감출 수 없다.** 이 둘을 포함한 감추기 아이콘이 모두 세로 띠에 있으므로,
띠까지 감출 수 있으면 되돌릴 길이 없어진다. 세로 띠가 사라지는 경우는 Zen 모드
하나뿐이고, Zen에는 `Escape`라는 탈출구가 있다(D-12).

이것이 앞서 열려 있던 문제를 닫는다 — 상단 바를 감추면 프레임리스라서 창
버튼(최소화·최대화·닫기)과 창을 끄는 자리가 함께 사라지는데, 세로 띠가 항상 보이므로
**아이콘 한 번으로 상단 바를 되돌릴 수 있다.** 창을 옮기거나 닫아야 하면 그렇게 한다.

**배제한 대안 (이어서)**

- **세로 띠도 감출 수 있게 한다.** 감추기 아이콘이 전부 거기 있어서, 감추는 순간
  되돌릴 수단이 사라진다. 배제한다.

## D-15. 새 탭은 항상 탭 줄 오른쪽 끝에 붙는다 — 위치는 나중에 끌어서 바꾼다

**선택**

새 탭이 생기는 자리는 **언제나 그 칸 탭 줄의 오른쪽 끝**이다. 방향을 고르는 선택지를
두지 않는다.

대신 **마우스로 끌어서** 두 가지를 한다 — 같은 탭 줄 안에서 순서 바꾸기, 다른 칸으로
옮기기(D-10).

**근거**

새 탭이 생길 자리가 하나로 고정되면 사용자가 눈으로 찾을 필요가 없다. 현재 탭 바로
오른쪽에 끼워 넣는 방식은 활성 탭이 어디냐에 따라 생기는 자리가 매번 달라져서, 방금
만든 탭을 다시 찾아야 한다.

위치를 고르는 선택지를 만들 이유도 없다. 순서가 마음에 안 들면 끌어서 옮기면 되고,
그 조작이 이미 있기 때문이다. 만들 때 방향을 정하는 것과 만든 뒤 옮기는 것 중 하나만
있으면 되는데, 옮기기는 어차피 필요하다.

칸은 다르다. 칸도 만든 뒤 끌어서 자리를 바꿀 수 있지만(dockview), 만들 때에도
방향(오른쪽·아래쪽)을 고른다 — VS Code가 그렇기 때문이다(D-13).

**배제한 대안**

- **현재 탭 바로 오른쪽에 끼워 넣는다.** 생기는 자리가 그때그때 달라진다. 배제한다.
- **새 탭도 왼쪽·오른쪽을 고르게 한다.** 매번 판단해야 하는데, 끌어서 옮길 수 있으므로
  얻는 것이 없다. 배제한다.
- **탭 순서를 고정하고 끌어서 바꾸지 못하게 한다.** 새 탭 자리를 오른쪽 끝 하나로
  정한 것이 그대로 불편으로 남는다. 배제한다.

## D-16. 탐색기 루트는 하나뿐이고, 바꾸는 방법은 폴더 열기 하나다

**선택**

트리 맨 위에 놓이는 최상위 폴더는 **항상 하나**다. 여러 폴더를 한 창에 나란히 묶지
않는다.

루트를 바꾸는 방법은 **폴더 열기(`Ctrl+O`)** 하나뿐이다. 다른 폴더를 열면 트리 전체가
그 폴더로 바뀐다. 최근에 연 폴더 목록은 메뉴에 둔다.

**근거**

VS Code는 여러 폴더를 한 창에 묶는 기능이 있다. 그것을 지원하면 "이 파일이 어느
루트에 속하나"가 트리·탭·경로 표시·설정 저장 등 거의 모든 규칙에 따라붙는다. 먼저
만들 세 앱 중 이것을 필요로 하는 것이 없다.

루트를 바꾸는 길을 하나로 두면 "지금 트리가 어느 폴더를 보고 있나"가 언제나 한 가지
조작의 결과다. 길이 여럿이면 그 상태가 어떻게 만들어졌는지 추적이 어려워진다.

`Ctrl+O`는 폴더·파일 열기의 관습적인 키다. 새로 정할 이유가 없다.

**배제한 대안**

- **여러 폴더를 한 창에 묶는다(VS Code의 멀티 루트).** 지금 필요 없는 복잡도를
  모든 규칙에 얹는다. 배제한다.
- **트리 안에서 상위 폴더로 거슬러 올라가 루트를 바꾼다.** 루트가 바뀌는 경로가
  둘이 되고, 실수로 루트가 바뀌기 쉽다. 배제한다.

## D-17. 파일 종류 아이콘은 VS Code 계열 두 세트만 쓴다

**선택**

파일 종류 아이콘은 **사용자가 고를 수 있는 두 가지 스타일**로 둔다. 둘 다 VS Code
쪽에서 온 것이며, 직접 그린 것은 쓰지 않는다.

| 이름 | 정체 | 성격 |
| --- | --- | --- |
| 기본 | **seti** (VS Code의 기본 파일 아이콘 테마) | 글꼴 글리프 + 색. 가볍고 차분하다 |
| 컬러 | **vscode-icons** | 확장자별 컬러 SVG. 종류가 한눈에 구분된다 |

앞선 `tab-explorer-templates`에는 세 번째로 "단순"(껍데기가 직접 그린 폴더·파일
아이콘 한 벌)이 있었다. **그것은 쓰지 않는다.**

**고르는 자리는 View 메뉴 하나다**(D-23). 세로 띠에는 두지 않는다 — 색 테마만큼
자주 바꾸는 것이 아니다.

껍데기는 어느 확장자가 어느 아이콘인지 알지 않는다. 트리 행의 이름과 펼침 여부만
넘기고 "무엇을 어떻게 그릴지"를 서술한 값 하나를 돌려받는 방식을 유지한다.

색 테마(흰색·회색·검정) 세 가지와는 **별개의 축**이다. 색 테마 세 개 × 아이콘 테마
두 개이지 아이콘을 색마다 따로 그리는 것이 아니다.

**근거**

D-3이 "아이콘을 직접 그리지 않는다"고 정했다. "단순"은 그 원칙에서 유일하게 벗어나
있던 자산이고, 이것까지 빼면 **손으로 그린 아이콘이 하나도 남지 않는다.** 만들고
유지하고 세 색 테마에 맞추는 일이 통째로 사라진다.

기준을 VS Code에 두는 것과도 맞다(INTENT 6절). 두 세트 모두 VS Code 사용자가 이미
보던 것이라, 새로 익힐 것이 없다.

둘을 남기는 이유는 성격이 다르기 때문이다. 확장자별 컬러 아이콘이 도움이 될 때가
있고 오히려 산만할 때가 있다. 폴더만 다루는 앱(파일 커맨터·멀티터미널)에서는 차분한
쪽이 낫다. 그 자리를 "단순" 대신 **seti**가 맡는다.

**라이선스** — 세트마다 다르다. 자세한 것은 [`refs/licenses.md`](refs/licenses.md).

- **seti** — MIT. 라이선스 본문을 함께 넣는다.
- **vscode-icons** — **코드는 MIT지만 아이콘은 CC BY-SA**이고, 브랜드 아이콘(회사
  로고 등)은 각자의 저작권 라이선스를 따른다. 저작자 표시가 필요하고, 아이콘을 고쳐
  쓰면 같은 조건으로 공개해야 한다. 고치지 않고 그대로 쓰면 표시로 충분하다.

앞선 프로젝트는 두 세트를 쓰면서 라이선스 본문을 함께 넣지 않았다. 이번에 채운다.

**바로잡음** — 이 항목은 처음에 "seti와 vscode-icons는 둘 다 MIT"라고 적었으나
사실이 아니었다. vscode-icons의 아이콘은 CC BY-SA다.

**배제한 대안**

- **직접 그린 "단순" 테마를 남긴다(앞선 프로젝트 방식).** 가장 가볍고 라이선스도
  걸리지 않는다는 이점이 있으나, 직접 그리지 않는다는 원칙(D-3)의 유일한 예외로 남고
  세 색 테마에 맞춰 유지해야 한다. 차분한 아이콘이 필요한 자리는 seti가 대신한다.
  배제한다.
- **하나로 고정한다(예: vscode-icons만).** 확장자 아이콘이 산만한 앱에서 끌 수 없다.
  배제한다.
- **VS Code 계열이 아닌 다른 아이콘 세트를 고른다.** 기준을 VS Code에 두기로 한
  INTENT 6절과 어긋나고, 사용자가 새로 익혀야 한다. 배제한다.

**남은 판단** — CC BY-SA가 부담이면 "컬러" 테마만 다른 세트로 바꿀 수 있다. 두 테마는
서로 독립이므로 "기본"에는 영향이 없다.

## D-18. 텍스트·코드 보기와 편집기를 껍데기가 기본으로 안고 간다 (monaco)

**선택**

VS Code의 편집 화면을 떼어낸 **monaco**를 껍데기의 기본 부품으로 반입한다. 앱이
따로 가져오지 않는다.

*켜는 기능* — 문법에 따른 색칠, 줄 번호, 찾기·바꾸기, 되돌리기/다시하기, 읽기 전용
모드. *끄는 기능* — 자동완성, 언어 서비스(오류 표시·정의로 이동), 미니맵, 다중 커서.
끄는 것들은 개발 도구의 기능이지 이 껍데기 위의 앱들이 쓰는 기능이 아니다(제1원칙).

*편집에 딸려 오는 것* — 저장, 탭에 고쳐짐 표시(●), 저장 안 한 탭을 닫거나 앱을 끌 때
경고. **탭에 표시를 찍는 것은 껍데기가, 무엇을 어떻게 저장할지는 앱이 맡는다.**
껍데기는 "이 탭은 고쳐졌다 / 저장됐다"는 상태만 받아 그린다.

**근거**

먼저 만들 세 앱 중 **파일 커맨터가 이것을 요구한다.** Total Commander처럼 두 칸을
두고 한쪽에서 고른 파일을 다른 쪽에서 보기(`F3`) · 편집(`F4`)하는 것이 그 앱의 핵심
동작이다. 마크다운 뷰어도 편집으로 갈 수 있다.

터미널과 성격이 다르다. 터미널은 멀티터미널 **한 앱만** 쓰지만, 텍스트를 보고 고치는
일은 이 껍데기 위에 올릴 앱들에서 **반복해서** 나온다. 앞으로 만들 앱이 파이썬
계산을 다루는 쪽이라도 설정 파일이나 스크립트를 열어 보는 일이 생긴다. 앱마다 같은
것을 따로 붙이면 "새 앱마다 드는 노력을 최소화한다"는 목적과 어긋난다.

`INTENT.md` 4절의 "범용 코드 편집기를 만들지 않는다"와는 어긋나지 않는다. 그 문장이
막는 것은 **편집기 제품을 만드는 것**이지, 앱들이 공유하는 부품으로 편집 화면을 두는
것이 아니다. 위에서 끄기로 한 기능들(자동완성·언어 서비스)이 그 경계다.

**배제한 대안**

- **앱이 가져온다(D-4에서 터미널을 다룬 방식).** 껍데기가 더 작게 유지되고 편집기를
  안 쓰는 앱이 그 무게를 지지 않는다는 이점이 분명하다. 그러나 여러 앱이 같은 것을
  반복해서 붙이게 되고, 그때마다 저장·고쳐짐 표시·닫을 때 경고를 각자 다시 만들어야
  한다. 터미널과 달리 쓰는 앱이 여럿이므로 배제한다.
- **껍데기에 넣되 앱이 켜고 끄게 한다.** 켜고 끄는 것 자체가 껍데기에 분기를 하나
  더한다. 배제한다.
- **monaco 대신 단순한 텍스트 영역을 직접 만든다.** 문법 색칠·찾기·되돌리기를 다시
  만드는 비용이 크고 D-2에 어긋나므로 배제한다.

**남은 판단** — 켜고 끄는 기능 목록은 위가 출발점이며, 실제로 써 보고 조정한다.
마크다운 뷰어를 편집까지 갈지는 그 앱의 결정이지 껍데기의 결정이 아니다.

## D-19. 앱이 "옆 칸에 열기"를 부를 수 있고, 탭 안의 키는 앱에게 간다

**선택**

파일 커맨터의 `F3` · `F4`를 성립시키려면 껍데기가 두 가지를 열어 주어야 한다.

**1. 옆 칸에 열기** — 앱이 "이 대상을 옆 칸의 탭에서 열어라"를 코드로 부를 수 있다.
사용자가 트리에서 `Ctrl+Enter`를 눌렀을 때와 같은 동작이며(D-9), 그 명령을 앱도
쓸 수 있게 여는 것이다. 옆 칸이 없으면 새로 만든다(오른쪽에 — D-13).

**2. 탭 안의 키는 앱에게 간다** — 포커스가 탭 안에 있을 때, 껍데기가 쓰지 않는 키는
그 탭의 보기에게 넘어간다. 파일 커맨터의 `F3`(보기) · `F4`(편집) · `F5`(복사) ·
`F6`(이동)과 여러 개 고르기의 `Space`가 여기 해당한다. 껍데기가 먼저 가져가는 키는
문서로 정해 두고, 그 밖은 전부 앱 몫이다.

`Space`는 트리에서 펼침/접힘이지만(D-9) 그것은 **포커스가 트리에 있을 때**다. 포커스가
탭 안에 있으면 트리 키 묶음이 적용되지 않으므로 부딪히지 않는다.

목록은 **가져가는 키**만 적지 않고, 흔히 껍데기 것이라고 오해하는 키를 **가져가지
않는다**고 함께 적는다. `Ctrl+S`(저장) · `F2`(이름 바꾸기) · `Delete`(삭제) ·
`Ctrl+Z` / `Ctrl+Y`(되돌리기·다시하기) · `Ctrl+C` / `Ctrl+V`가 그것이다. 저장은 앱이
하고(D-18), 만들기·이름 바꾸기·삭제도 앱이 한다(D-30 · D-22). 껍데기가 이 키들을
가져가면 그 순간 리소스 종류를 아는 판단이 껍데기로 들어온다. 적어 두지 않으면 앱마다
다르게 정하거나, 나중에 껍데기가 슬그머니 가져가게 된다.

**3. 앱이 칸 배치를 물을 수 있다** — 앱이 "지금 내가 어느 칸에 있나", "옆 칸에는
무엇이 열려 있나"를 물을 수 있다. 파일 커맨터가 고른 파일을 **반대편 칸의 폴더로**
복사·이동하려면 반대편이 어느 폴더를 보고 있는지 알아야 하는데, 칸 배치는 껍데기만
안다.

**근거**

파일 커맨터의 핵심 동작이 "왼쪽에서 고른 것을 오른쪽에서 본다"인데, 지금 껍데기는
**탐색기에서 고르는 경우만** 다룬다(D-5). 탭 안의 목록에서 고르는 경우는 앱의 일이고,
그 결과를 옆 칸에 띄우는 것은 껍데기만 할 수 있다. 이 자리가 열려 있지 않으면 앱이
껍데기 밖에서 탭을 직접 건드려야 하고, 그 순간 "공통 코어 수정 0줄"이 깨진다.

복사·이동도 같다. "반대편 칸으로"라는 말 자체가 칸 배치를 아는 쪽만 할 수 있는
판단이다. 다만 껍데기는 **어느 칸에 무엇이 열려 있는지만 알려주고**, 복사와 이동
자체는 하지 않는다. 파일을 옮기는 일은 리소스 종류를 아는 앱의 몫이다(INTENT 3절).

키도 같다. 껍데기가 모든 키를 가져가면 앱이 자기 단축키를 가질 수 없다. 반대로
앱이 모든 키를 가져가면 트리 조작(D-9)이 깨진다. 그래서 **껍데기가 가져가는 키를
목록으로 정하고 나머지를 넘기는** 방식으로 가른다.

**배제한 대안**

- **앱이 껍데기의 탭·칸을 직접 조작한다.** 껍데기의 내부 상태가 앱에 노출되어 규칙이
  깨질 자리가 열린다. 배제한다.
- **`F3` · `F4`를 껍데기의 키로 정한다.** 껍데기가 "보기"와 "편집"이라는 앱의 개념을
  알게 되어 "껍데기는 리소스 종류를 모른다"(INTENT 3절)에 어긋난다. 배제한다.
- **키를 앱이 먼저 받고 안 쓰면 껍데기로 넘긴다.** 앱이 실수로 트리 키를 삼키면
  탐색기가 죽는데 원인을 찾기 어렵다. 껍데기 우선이 안전하다. 배제한다.

## D-20. 빈 상태에는 아무것도 그리지 않는다

**선택**

폴더를 아직 열지 않았을 때의 트리 자리, 사용자가 방금 추가한 빈 탭의 안쪽, 그리고
마지막 칸의 탭이 모두 닫혔을 때 남는 그 칸(D-26)에는 **아무것도 그리지 않는다.**
안내 문구도 버튼도 두지 않고 빈 면으로 둔다.

VS Code의 환영 뷰(Welcome View)에 해당하는 것을 만들지 않는다.

**근거**

폴더를 여는 길은 이미 하나로 정해져 있다 — 메뉴의 폴더 열기와 `Ctrl+O`(D-16). 빈
트리에 [폴더 열기] 버튼을 두면 같은 일로 가는 길이 둘이 된다. D-16이 "루트를 바꾸는
길은 하나"로 정한 것과 어긋난다.

안내 문구도 만들고 유지해야 하는 것이다. 문구를 정하고, 세 색 테마에 맞추고, 두
갈래에서 같게 보이는지 확인해야 한다. 제1원칙(최소 구현)에 비추어 그만한 값어치가
없다고 본다.

**완료 조건과의 관계** — BRIEF의 "빈 상태" 시나리오는 이 결정으로 판정 가능해진다.
정해진 결과는 **"빈 면이 나오고 아무 동작도 일어나지 않는다"**이다. 무엇이 그려져야
하는지가 아니라 무엇도 그려지지 않아야 하는지가 기준이 된다.

**배제한 대안**

- **한 줄 안내와 버튼 하나를 둔다(VS Code의 환영 뷰에 해당).** 처음 쓰는 사람이
  무엇을 눌러야 할지 알 수 있다는 이점이 있으나, 폴더 여는 길이 둘이 되고 유지할
  것이 늘어난다. 배제한다.
- **빈 트리에 최근에 연 폴더 목록을 보인다.** 편하지만 빈 화면이 아닌 것을 하나 더
  만드는 셈이고, 최근 폴더는 이미 메뉴에 있다(D-16). 배제한다.

## D-21. 실패도 진행도 하단 바 한 줄로만 알린다

**선택**

오류·경고와 오래 걸리는 작업의 진행 표시를 **모두 하단 바(상태 표시줄)에 한 줄로**
보인다. 오른쪽 아래에 떠올랐다 사라지는 알림 상자를 만들지 않는다. 알림이 쌓이는
목록이나 지난 알림을 다시 보는 자리도 두지 않는다.

**근거**

떠오르는 알림 상자를 만들려면 그 상자를 그리고, 겹칠 때 쌓고, 시간이 지나면 지우고,
세 색 테마에 맞추고, 두 갈래에서 같게 보이는지 확인해야 한다. 하단 바는 **이미
있는 자리**라 새로 만들 것이 없다.

화면을 가리지 않는 것도 이유다. 오른쪽 아래는 탭 영역 위에 겹치는데, 터미널이나
파일 목록의 아래쪽이 자주 가려진다.

**받아들이는 단점** — 하단 바는 눈에 덜 띄어서 오류를 놓칠 수 있다. 이것을 알고
고른다. 놓치는 것이 실제로 문제가 되면 그때 알림 상자를 더한다.

**배제한 대안**

- **오류는 오른쪽 아래 짧은 메시지로, 진행은 하단 바로 나눈다.** 실패가 눈에 잘
  띈다는 이점이 분명하지만, 그리는 장치를 하나 더 만들어야 하고 탭 영역을 가린다.
  배제한다.
- **껍데기는 자리만 주고 문구와 모양은 앱이 정한다(D-4 · D-11 방식).** 알림의 생김새가
  앱마다 달라지면 같은 껍데기를 쓴다는 느낌이 깨진다. 무엇을 알릴지는 앱이 정하되
  **어떻게 보일지는 껍데기가 정한다.** 배제한다.
- **알림이 쌓이는 목록을 둔다(VS Code의 알림 센터).** 지난 알림을 다시 보는 요구가
  아직 없다. 배제한다.

## D-22. 우클릭 메뉴는 껍데기가 장치만 주고 항목은 앱이 채운다

**선택**

트리의 항목 위, 탭 제목 위에서 오른쪽 버튼을 눌렀을 때 뜨는 메뉴를 둔다. 껍데기는
**메뉴를 띄우고 그리는 장치만** 제공한다 — 어디에 뜨는지, 어떻게 생겼는지, 어떻게
닫히는지, 키보드로 어떻게 오르내리는지.

**무슨 항목이 들어갈지는 앱이 정한다.** 껍데기가 기본으로 넣는 항목은 없다.

**기본값은 "사용 안 함"이다.** 껍데기만 있는 상태에서는 오른쪽 버튼을 눌러도 아무
일이 일어나지 않는다. 앱이 항목을 정의하고, 사용자가 메뉴에서 켜야 뜬다. 켜고 끄는
항목은 View 묶음에 둔다(D-23).

**근거**

무슨 항목이 뜨는지는 앱마다 다르다. 파일 커맨터는 보기·편집·복사·삭제가 필요하고,
마크다운 뷰어는 옆 칸에 열기 정도면 된다. 껍데기가 이것을 알면 "껍데기는 리소스
종류를 모른다"(INTENT 3절)가 깨지고, 다음 앱이 쓰지 않는 항목을 이고 가게 된다.
터미널(D-4)과 세로 띠 항목(D-11)을 다룬 방식과 같다.

생김새는 껍데기가 정한다. 알림에서와 같은 이유다 — **무엇을 담을지는 앱이, 어떻게
보일지는 껍데기가**(D-21).

기본 항목을 하나도 넣지 않는 이유는 D-13에서 칸 명령을 뺐기 때문이다. 그러고 나면
껍데기가 넣을 만한 것으로 탭의 "닫기"가 남는데, 탭에는 이미 닫기 버튼이 있어
같은 일로 가는 길이 둘이 된다.

**배제한 대안**

- **껍데기가 탭 쪽에 "닫기 / 다른 탭 모두 닫기"를 기본으로 넣는다.** 모든 앱에서 같은
  항목이 보이는 일관성은 있으나, 껍데기가 탭 메뉴의 내용을 알게 되고 닫기로 가는 길이
  둘이 된다. 배제한다.
- **우클릭 메뉴를 아예 두지 않는다.** 파일 커맨터가 항목에 대고 무언가를 하는
  도구라, 그 명령을 전부 키나 도구 막대 버튼으로만 둬야 한다. 배제한다.
- **기본값을 "사용함"으로 둔다.** 앱이 항목을 정의하지 않았는데 오른쪽 버튼을 누르면
  빈 메뉴가 뜨거나 아무 반응이 없어, 고장인지 원래 그런지 구별되지 않는다. 꺼 두면
  "안 되는 것"이 정해진 결과가 된다. 배제한다.
- **생김새까지 앱이 정한다.** 앱마다 메뉴가 달라 보이면 같은 껍데기를 쓴다는 느낌이
  깨진다. 배제한다.

## D-23. 메뉴는 File · View · Help 세 묶음, 하단 바는 경로와 앱 정보

**선택**

*메뉴* — 상단 바의 햄버거 버튼(`≡`)을 누르면 세 묶음이 나온다.

| 묶음 | 항목 |
| --- | --- |
| **File** | 폴더 열기(`Ctrl+O`) · 최근 폴더 · 끝내기 — **D-31에서 탭 닫기(`Ctrl+W`) · 폴더 닫기를 더해 다섯이 되었다** |
| **View** | 탐색기 접기/펴기 · 상단 바 감추기/보이기 · 하단 바 감추기/보이기 · Zen 모드 · 테마 바꾸기 · **아이콘 테마 바꾸기**(D-17) · 좌우 스플릿 · 상하 스플릿(D-13) · 활성 칸 탭 모두 닫기(D-26) · **우클릭 메뉴 사용**(기본 꺼짐 — D-22) |
| **Help** | 정보 |

*하단 바* — 왼쪽에 지금 탭이 가리키는 대상의 경로, 오른쪽에 앱 이름·버전·실행
갈래. 그 사이가 오류·진행 메시지가 뜨는 자리다(D-21). **앱이 자기 항목을 하나 더
붙일 수 있는 자리**를 남긴다.

메뉴는 껍데기가 채운다. 앱이 항목을 더할 수 있으나, 위 세 묶음은 모든 앱에 공통으로
있다. **어느 묶음에 어떻게 더하는지는 D-31이 정한다** — File에만 더할 수 있고,
껍데기 항목 아래 가름선 다음에 붙는다.

**근거**

세 묶음은 VS Code를 비롯한 데스크톱 앱의 관습이라 어디에 무엇이 있는지 찾을 필요가
없다. 항목이 나중에 늘어도 들어갈 자리가 이미 정해져 있다.

View에 든 것은 세로 띠의 아이콘과 겹친다. 이것은 중복이 아니라 D-7에서 정한 역할
분담이다 — **메뉴는 전부를 담고, 세로 띠는 자주 쓰는 것만 담는다.** 세로 띠의 항목은
앱이 바꿀 수 있으므로(D-11), 어떤 앱이 아이콘을 빼더라도 메뉴에는 남아 있어야 한다.

메뉴를 껍데기가 채우는 것은 세로 띠·우클릭 메뉴와 반대다. 그쪽은 앱마다 다른 것을
담지만, 메뉴에 든 것은 **폴더 열기·화면 접기·테마처럼 모든 앱에 공통인 껍데기의
기능**이기 때문이다.

**배제한 대안**

- **묶음 없이 한 목록으로 늘어놓는다.** 지금은 항목이 적어 한 번 덜 누르는 이점이
  있으나, 항목이 늘면 어디에 넣을지가 매번 판단이 된다. 배제한다.
- **메뉴도 앱이 채운다(세로 띠·우클릭 메뉴 방식).** 메뉴에 든 것은 대부분 껍데기의
  기능이라 앱마다 다를 이유가 없다. 배제한다.
- **하단 바에 앱 자리를 남기지 않는다.** 앱이 상태를 보일 곳이 없어져 화면 안에
  자체 표시줄을 만들게 된다. 배제한다.

## D-24. 칸·탭·보기 수명은 dockview를 가져다 쓴다 — 확인을 거쳐 정했다

**선택**

칸 나누기(좌우·상하), 2차원 격자 배치, 칸 크기 조절, 탭 줄, 탭 끌어 옮기기(가장자리로
끌어 새 칸 만들기 포함), 칸 사이 이동, 마지막 탭이 닫히면 칸이 사라지는 것, 배치
저장·복원 — 이 덩어리를 **`dockview-core`(MIT)** 로 가져다 쓴다. 직접 짜지 않는다.

**안 보이는 탭의 처리** — 껍데기 기본은 dockview의 기본값(안 보이는 동안 화면 요소를
떼어 두는 쪽)으로 둔다. 떼어지면 곤란한 보기는 **앱이 그 탭만 "항상 그려 두기"로
올린다.** 터미널이 그런 경우다.

**근거**

D-2가 "이미 잘 만들어진 것을 다시 만드는 비용이 크고 최소 구현에 어긋난다"고 정했다.
codicons(D-3) · monaco(D-18)에 적용한 판단이 여기에도 적용되며, 덩어리는 이쪽이 가장
크다. 그리고 앞선 프로젝트가 무너진 자리가 정확히 여기다(BRIEF 1절 — 탭 이동, 분할
해제, 선택과 포커스). 같은 것을 손으로 다시 짜면 같은 실패를 반복할 가능성이 높다.

칸 나누기와 크기 조절 코드가 **VS Code의 해당 부분에서 나왔다고** 저장소가 밝히고
있어, "VS Code 방식을 따른다"는 기준(INTENT 6절)과 어긋나지 않는다. 의존성이 없고
MIT이며, 화면 프레임워크 없이 쓸 수 있다.

**확인한 것** — 채택 전에 BRIEF 완료 조건의 "보기 인스턴스가 다시 만들어지지 않는다"를
실제로 시험했다. `dockview-core` 8.2.0을 설치하고, 인스턴스마다 도장을 찍고 계속 도는
타이머와 DOM 안에만 있는 상태를 붙인 패널을 만들어 헤드리스 브라우저에서 두 가지를
했다 — 같은 칸 안에서 탭을 갔다가 되돌아오기, **다른 칸으로 옮기기.**

두 렌더 방식 모두에서 **만들어진 횟수 1 · 폐기 0 · 인스턴스 도장 동일 · 타이머 연속 ·
DOM 상태 유지**로 나왔다. 옮겨도 다시 만들어지지 않는다.

같은 시험에서 차이도 드러났다. 기본 방식은 탭이 활성이 아닌 동안 화면 요소를 DOM에서
**떼어 둔다.** 인스턴스는 살아 있지만 화면에서 분리되므로, 크기를 재서 동작하는
보기(xterm 같은 터미널)는 다시 붙일 때 크기를 맞춰야 한다. "항상 그려 두기"는 떼지
않는 대신 안 보이는 탭도 계속 그린다. 그래서 기본은 가벼운 쪽에 두고 필요한 보기만
앱이 올리게 한다 — 껍데기가 어느 보기가 터미널인지 알 필요가 없으므로 "껍데기는
리소스 종류를 모른다"(INTENT 3절)도 지켜진다.

**배제한 대안**

- **직접 짠다(참조 재구현).** 규칙을 온전히 장악한다는 이점이 있으나, D-8이 2차원
  격자 배치를 그대로 받으면서 난이도가 올라갔다. 크기 조절·끌어 놓기·2차원 배치·배치
  저장·보기 수명까지 전부 우리 몫이 되고, 그것이 앞선 프로젝트가 실패한 지점이다.
  배제한다.
- **모든 탭을 "항상 그려 두기"로 둔다.** 떼어짐 문제가 사라져 단순하지만, 안 보이는
  탭이 전부 계속 그려진다. 멀티터미널처럼 탭이 여럿인 앱에서 부담이 커진다. 배제한다.
- **떼어짐을 앱이 모르게 껍데기가 알아서 처리한다.** 어느 보기가 크기에 민감한지는
  껍데기가 알 수 없다. 배제한다.

**메모** — `dockview-core`는 `<script>` 하나로 읽히는 묶음본(UMD)도 함께 배포한다.
즉 **dockview 때문에 빌드가 필요한 것은 아니다.** D-1의 빌드 전제는 그대로 유효하나,
그 근거 중 "빌드형 라이브러리를 쓰려면"이라는 부분은 dockview에 해당하지 않는다.

## D-25. 빌드는 Vite로 하고, 산출물 한 벌을 두 갈래가 함께 읽는다

**선택**

D-1이 전제한 빌드를 **Vite**로 한다. 웹 자산을 **한 벌로** 빌드하고, 그 산출물을
Electron과 pywebview가 **똑같이** 읽는다. 갈래마다 다른 빌드를 두지 않는다.

**근거**

산출물이 한 벌이어야 "두 갈래가 같은 사용자 동작에 같은 결과를 낸다"는 완료 조건이
**구조적으로** 보장된다. 갈래별로 빌드가 갈리면 한쪽에서만 나타나는 차이가 생길
자리가 만들어지고, 그때부터 동등성을 사람이 매번 확인해야 한다.

빌드 자체는 monaco(D-18) 때문에 필요하다. dockview는 `<script>` 하나로 읽히는
묶음본이 있어 빌드 없이도 되지만(D-24), monaco는 그렇지 않다.

같은 일을 하는 도구가 여럿 있는데(webpack · rollup · esbuild · parcel) Vite를 고르는
이유는 설정이 가장 적고, 고치면 즉시 화면에 반영되는 개발 모드가 기본으로 들어 있기
때문이다. 설정이 적다는 것은 그 자체로 최소 구현에 부합한다.

**배제한 대안**

- **webpack.** 오래되어 자료가 많다는 이점이 있으나 설정이 길고, 개발 중 즉시 반영을
  따로 붙여야 한다. 배제한다.
- **rollup · esbuild를 직접 쓴다.** 더 낮은 층이라 손댈 것이 많다. Vite가 내부적으로
  이들을 쓰므로 굳이 직접 다룰 이유가 없다. 배제한다.
- **갈래마다 따로 빌드한다.** 각 갈래에 맞춘 최적화가 가능하지만, 동등성을 구조가
  아니라 확인으로 지켜야 한다. 배제한다.
- **무빌드로 돌아간다(D-1 뒤집기).** dockview는 되지만 monaco가 걸린다. D-18에서
  monaco를 껍데기에 넣기로 이미 정했으므로 배제한다.

## D-26. 칸은 명시적으로 닫지 않는다 — 탭이 모두 닫히면 사라지고, 마지막 한 칸은 남는다

**선택**

**칸 자체를 닫는 전용 기능을 두지 않는다.** 세로 띠·메뉴·우클릭 어디에도 "칸
닫기/삭제" 항목이 없다. 칸은 탭을 통해서만 사라진다(아래).

칸은 그 칸의 탭이 `×` 또는 `Ctrl+W`로 하나씩, 또는 한꺼번에 모두 닫혀서 **탭이 0개가
되면 사라진다.** 남은 칸들이 그 자리를 나눠 갖는다(dockview — D-24). 닫힌 탭의 보기는
그때 폐기된다(D-24). 탭을 다른 칸으로 옮기거나 살아남은 칸에 나눠 붙이지 않는다.

한꺼번에 닫는 것은 **View 메뉴의 "활성 칸 탭 모두 닫기" 하나로만** 한다. 탭 줄이나
세로 띠에는 아이콘을 두지 않는다. 활성 칸이 빈 칸이어도(탭 0개) 이 항목은 메뉴에
그대로 있으며, 눌러도 결과가 이미 빈 칸이라 바뀌는 것이 없다.

**칸이 사라져도 최소 한 칸은 남는다.** 마지막 칸의 마지막 탭까지 닫으면 그 칸은
탭 없는 빈 면으로 남는다(D-20). 편집기 영역이 통째로 없어지는 상태는 두지 않는다.
그 빈 칸에서 다시 시작하는 길은 셋이다 — 탐색기에서 파일 고르기(D-5), 세로 띠의
스플릿 아이콘, View 메뉴.

**근거**

VS Code 동작을 기본으로 삼는다(divergence는 Zen 하나뿐 — D-12). VS Code에는 편집기
그룹을 닫는 전용 버튼이 없다 — 그룹은 비면 사라지고(`workbench.editor.closeEmptyGroups`
기본값), 마지막 그룹 하나는 늘 남는다. 그대로 따른다.

전용 "칸 닫기"를 두면 조작이 하나 늘고, 그 결과(탭은 어디로 가나, 어느 칸이 활성이
되나)를 정하는 규칙이 따라붙는다. 탭을 하나씩 닫아 칸을 비우는 길이 이미 있으므로
없어도 된다.

마지막 칸을 빈 채로 남기는 것은 "편집기 영역은 항상 있다"는 VS Code의 전제와 같다.
칸이 0개가 되도록 두면 스플릿 아이콘이 기준으로 삼을 칸이 없어지고, D-5의 "현재
칸"·D-13·D-19가 전제하는 자리가 사라진다. 빈 칸 하나를 남기면 그 자리가 항상
성립한다.

**배제한 대안**

- **"칸 닫기/삭제" 아이콘을 세로 띠와 메뉴에 둔다.** 한때 이렇게 정했다(옛 D-26).
  VS Code에 없는 조작이고, 탭을 비우는 길이 이미 있어 중복이다. 배제한다.
- **칸의 탭을 옆 칸으로 옮긴다.** 닫았는데 내용이 남아 조작과 결과가 어긋난다.
  "어느 칸으로", "탭 순서 어디에", "무엇이 활성" 규칙이 새로 필요하다. 배제한다.
- **마지막 칸까지 없애 편집기 영역을 비운다(칸 0개 허용 — 옛 D-26).** 스플릿의 기준
  칸이 사라지고, 첫 칸을 다시 만드는 특수 규칙이 필요해진다. Zen 외의 divergence가
  하나 더 생긴다. 배제한다.

## D-27. 다시 열 때 되살리는 것은 마지막에 연 폴더뿐이다

**선택**

앱을 껐다 켜면 **마지막에 열었던 루트 폴더가 탐색기에 다시 나타난다.** 그것뿐이다.

칸 배치, 열려 있던 탭, 활성 탭, 트리의 펼침 상태는 되살리지 않는다. 시작하면 폴더
하나가 열린 채 오른쪽은 빈 칸 하나다(D-26 · D-20).

**근거**

폴더를 다시 여는 것은 켤 때마다 반복되는 일이라 아낄 값어치가 있다. 반면 탭과 칸은
그때그때 다르고, 되살리면 "그 파일이 사라졌으면", "그 폴더가 없어졌으면", "터미널
세션은 되살릴 수 없는데 탭만 되살아나면" 같은 경우를 전부 다뤄야 한다. 특히 터미널은
프로세스가 이미 죽었으므로 되살릴 수 있는 것이 아니다(D-4).

dockview가 배치 저장·복원을 제공하지만(D-24) 쓸 수 있다는 것과 써야 한다는 것은
다르다. 되살릴 것이 적을수록 켤 때의 상태가 하나로 정해진다.

**배제한 대안**

- **칸 배치와 열려 있던 탭까지 되살린다.** 편하지만 사라진 대상과 되살릴 수 없는
  세션을 다루는 규칙이 줄줄이 따라온다. 배제한다.
- **아무것도 되살리지 않는다.** 켤 때마다 폴더를 다시 고르는 것은 반복 비용이 크다.
  배제한다.

## D-28. 저장하지 않은 채 닫으려 하면 확인 창으로 묻는다

**선택**

고쳐 놓고 저장하지 않은 탭을 닫으려 하거나 앱을 끄려 하면 **확인 창**이 뜬다.
데스크톱 앱에서 흔히 쓰는 세 버튼을 그대로 쓴다.

| 버튼 | 결과 |
| --- | --- |
| **저장** | 저장한 뒤 닫는다 |
| **저장 안 함** | 고친 것을 버리고 닫는다 |
| **취소** | 닫지 않는다. 고친 내용도 그대로 남는다 |

새로 만든 방식이 아니라 사용자가 다른 프로그램에서 이미 아는 방식이다. 무엇을
누르면 무엇이 되는지를 배울 필요가 없다.

**D-21과의 경계** — D-21은 알림 상자를 만들지 않기로 했다. 그것과 어긋나지 않는다.
둘은 성격이 다르다.

| | 무엇 | 어디에 |
| --- | --- | --- |
| **알림** | 일방적으로 알려 주기만 한다. 답을 받지 않는다 | 하단 바 (D-21) |
| **확인** | 사용자의 답을 받아야 다음이 정해진다 | 확인 창 (이 결정) |

하단 바로는 답을 받을 수 없으므로 확인은 창이어야 한다. 반대로 답이 필요 없는 것을
창으로 띄우지 않는다.

**근거**

저장 안 한 것을 말없이 버리는 것은 되돌릴 수 없는 손실이다. 그런 것은 사용자에게
묻는다.

세 버튼인 이유는 셋 다 실제로 필요한 답이기 때문이다. 저장하고 닫고 싶을 때, 실수로
고친 것을 버리고 닫고 싶을 때, 닫는 것 자체를 그만두고 싶을 때가 모두 있다. 이것은
새로 발명하지 않는다는 원칙(INTENT 6절)이 UI 관습에도 적용되는 자리다.

**배제한 대안**

- **[취소]와 [저장하기] 둘만 둔다.** 버리고 닫는 길이 막혀 실수로 고친 파일도 반드시
  저장해야 한다. 되돌리기로 되돌린 뒤 닫는 우회로가 있지만, 흔한 방식과 달라 사용자가
  버튼을 보고 멈칫하게 된다. 배제한다.
- **묻지 않고 그냥 닫는다.** 손실이 조용히 일어난다. 배제한다.
- **하단 바에 경고만 띄우고 닫는다.** 답을 받을 수 없으므로 경고가 아니라 사후
  통보가 된다. 배제한다.

## D-29. 시각 체계는 VS Code를 따른다 — 세 테마(흰색·회색·검정), tab-explorer 자산은 안 쓴다

**선택**

색·글꼴·간격·모서리 같은 시각 체계는 **VS Code를 기준으로 새로 정한다.**
`tab-explorer-templates`가 정의한 값 — 글꼴(`Segoe UI` · `Cascadia Mono`), 글자
크기 12px, 간격 4/8/12/16px, 모서리 6px, 색 토큰 전부 — 은 **하나도 쓰지 않는다.**

**색 테마는 셋이다 — 흰색 · 회색 · 검정.**

- **흰색 · 검정** — VS Code의 기본 밝은 테마(Light Modern)와 어두운 테마(Dark Modern)를
  따른다. 색 토큰의 이름 체계와 값을 그 두 테마에서 가져온다.
- **회색** — VS Code에는 대응하는 기본 테마가 없다. **흰색 테마와 검정 테마 배경의
  산술 중간**(밝기 기준 — 대략 중간 회색, `#808080` 계열 L\* ≈ 54~56)에 배경을 두고,
  나머지 토큰도 두 테마의 대응 값 사이에서 같은 비율로 잡는다. 색상·채도는 VS Code
  팔레트 계열을 유지한다. tab-explorer의 값은 참조하지 않는다.

세 테마는 앱들이 공유하는 하나의 기준으로 정돈된 상태를 유지한다(BRIEF 3절). 어느
테마에서든 codicons·파일 종류 아이콘은 색만 바뀐다(D-3 · D-17). 정확한 토큰 값은
SPEC에서 정한다.

**근거**

INTENT 6절이 "VS Code 방식을 따른다"이고, BRIEF 2절이 "배치·간격·구현 방식은
물려받지 않는다", BRIEF 3절이 "겉보기는 처음부터 다시 구성한다"고 못 박았다.
`tab-explorer-templates`는 VS Code를 모르는 상태에서 시행착오로 만들어졌고, 그 시각
값을 가져오면 "VS Code를 따른다"와 "앞선 것을 안 물려받는다"가 둘 다 흔들린다.
그래서 tab-explorer의 값은 색·글꼴·간격 어느 것도 참조하지 않는다.

회색 테마는 VS Code에 대응 기본 테마가 없어 새로 정해야 한다. 흰색과 검정의 산술
중간에 두면 규칙이 하나로 단순하고("두 테마의 가운데"), 세 테마가 밝기 축에서
고르게 벌어진다. 어느 한 값을 외부에서 빌리지 않으므로 참조 대상이 남지 않는다.

**배제한 대안**

- **`tab-explorer-templates`의 세 색 토큰을 그대로 가져와 다듬는다.** 이미 세 테마가
  정돈돼 있어 빠르지만, VS Code가 아닌 값을 시각 체계의 바탕에 두게 된다. INTENT 6절·
  BRIEF 2·3절과 어긋나므로 배제한다.
- **회색 배경 밝기를 `tab-explorer-templates`의 회색(`#353b44`, L\* ≈ 25)에서 가져온다.**
  한때 이렇게 정했다. 실사용으로 검증된 값이라는 이점이 있으나, tab-explorer의 어떤
  값도 쓰지 않기로 하면서 참조 자체를 없앴다. 배제한다.
- **회색 테마를 두지 않고 흰색·검정 둘만 둔다(VS Code 기본과 동일).** 가장 단순하지만
  BRIEF 3절이 "세 색상 테마"를 명시하고 D-3·D-17이 그 위에 서 있다. 배제한다.
- **글꼴·간격까지 VS Code 값을 픽셀 단위로 복제한다.** 기준으로 삼는 것과 복제하는
  것은 다르다. VS Code를 기준으로 새로 정하되 두 갈래·세 테마에서 일관되면 되고,
  세부 수치는 SPEC에서 정한다. 배제한다.

## D-30. 탐색기 뷰 제목줄을 둔다 — 접기·새로 고침은 껍데기, 만들기는 앱

**선택**

VS Code처럼 탐색기 위에 **뷰 제목줄**을 두고 오른쪽에 액션 아이콘을 놓는다. D-9의
외형 항목이 이미 이것을 요구했는데 시나리오와 `SPEC`으로 내려오지 않았다. 넷을
성격에 따라 가른다.

| 액션 | 누가 하나 |
| --- | --- |
| **모두 접기** | 껍데기. 순수 트리 상태이고 키(`Ctrl+←`)가 이미 있다(D-9). 버튼만 더한다 |
| **새로 고침** | 껍데기가 버튼을 두고, 다시 읽는 일은 트리 공급자(갈아끼우는 자리)에게 "다시 물어봐"를 부른다. 무엇을 다시 읽는지는 껍데기가 모른다 |
| **새 파일 · 새 폴더** | 껍데기는 **장치만** 준다 — 트리에 인라인 이름 입력 행을 그리고 `Enter`·`Escape`를 처리한다. 이름을 받아 실제로 만드는 것은 앱이다 |

껍데기가 기본으로 넣는 액션은 **모두 접기 · 새로 고침 둘**이다. 새 파일·새 폴더는
앱이 D-31의 표면으로 꽂는다. 앱이 꽂지 않으면 그 아이콘은 없다.

**근거**

"껍데기는 리소스 종류를 모른다"(INTENT 3)를 지키면서 VS Code의 익숙한 자리를
물려받는 방법은 이 갈래뿐이다. 껍데기가 "새 파일"을 실제로 만들면 파일이 무엇인지
아는 코드가 껍데기로 새고, 폴더 축 앱(멀티터미널)이 쓰지 않는 기능을 이고 간다.

장치는 껍데기가, 내용은 앱이 — 이 갈래는 우클릭 메뉴(D-22)와 알림(D-21)에서 이미
두 번 쓴 것과 같다. 세 자리가 같은 규칙을 따르면 앱을 만드는 사람이 매번 다시
배우지 않는다.

새로 고침을 껍데기에 두는 것은, 그것이 "지금 보이는 것을 다시 물어봐"일 뿐 무엇을
물어보는지는 모르기 때문이다. 트리 공급자가 이미 갈아끼우는 자리이므로 새 표면이
늘지 않는다.

**배제한 대안**

- **넷 다 껍데기가 한다.** VS Code와 가장 같아 보이지만 파일·폴더 생성 코드가
  껍데기에 들어가 INTENT 3이 깨진다. 배제한다.
- **넷 다 앱이 한다(껍데기는 자리만).** 껍데기가 더 단순해지지만, 모두 접기는 이미
  껍데기의 키(`Ctrl+←`)이고 새로 고침도 껍데기의 트리가 하는 일이라 같은 일을 앱마다
  다시 짜게 된다. 앱마다 이름 입력 모양이 달라지는 것도 "같은 껍데기를 쓴다"는 느낌을
  깬다. 배제한다.
- **뷰 제목줄을 두지 않고 우클릭 메뉴로만 만들기를 연다.** 자리가 하나 줄지만
  우클릭 메뉴는 기본 꺼짐이라(D-22) 껍데기만 있는 상태에서 새로 고침·모두 접기로
  가는 길이 없어진다. 배제한다.
- **이름 바꾸기·삭제도 뷰 제목줄에 둔다.** VS Code도 제목줄에 두지 않는다. 이 둘은
  항목을 고른 뒤의 동작이라 우클릭 메뉴(D-22)와 앱 키(D-19)가 맡는 자리다. 배제한다.

## D-31. 앱이 File 묶음과 뷰 제목줄에 항목을 더한다 — View·Help는 껍데기만 채운다

**선택**

D-23은 "앱이 항목을 더할 수 있으나"라고만 적고 어디에 어떻게인지를 정하지 않았다.
여기서 정한다.

| 자리 | 앱이 더할 수 있나 |
| --- | --- |
| **File 묶음** | **그렇다.** 껍데기 항목 뒤에 가름선을 두고 그 아래에 붙는다 |
| **탐색기 뷰 제목줄** | **그렇다.** 껍데기 액션(모두 접기·새로 고침 — D-30) 왼쪽에 붙는다 |
| **View 묶음** | 아니다. 전부 껍데기 기능이다 |
| **Help 묶음** | 아니다 |

File 묶음의 껍데기 항목을 다음 다섯으로 한다. **탭 닫기**와 **폴더 닫기**를 더한 것이다.

| 항목 | 결과 |
| --- | --- |
| 폴더 열기(`Ctrl+O`) | D-16 |
| 최근 폴더 | D-16 |
| 탭 닫기(`Ctrl+W`) | 활성 탭을 닫는다. 키로 닫는 것과 같다(D-26) |
| 폴더 닫기 | 루트를 비운다. 트리가 폴더를 열지 않은 빈 상태로 돌아간다(D-20). 탭과 칸은 건드리지 않는다 |
| 끝내기 | |

앱이 더하는 것의 예 — 파일 열기 · 최근 파일 · 저장 · 다른 이름으로 저장 · 새 파일 ·
새 폴더. **껍데기는 이 이름들을 모른다.** 앱이 이름과 키와 할 일을 함께 준다.

껍데기가 넣는 항목의 목록과 순서는 앱이 바꾸거나 뺄 수 없다. 앱이 더한 항목은
가름선 아래에만 놓인다.

**근거**

File 묶음에 드는 것은 **대상을 열고 닫고 저장하는 일**이라 앱마다 다르다. 텍스트
에디터는 저장이 필요하고 마크다운 뷰어는 필요 없다. 반면 View에 든 것은 화면 접기·
테마처럼 모든 앱에 공통인 껍데기 기능이라 앱이 더할 것이 없다(D-23). 그래서 한
묶음만 연다.

이 자리가 없으면 저장·파일 열기 같은 명령이 **키에만** 존재한다. 메뉴에 없는 명령은
있는지조차 알 수 없어, 앱마다 자체 도구 막대를 화면 안에 만들게 된다 — 하단 바에
앱 자리를 남긴 것(D-23)과 같은 이유로 배제해야 할 결과다.

검증 앱 셋 중 **파일 커맨터**가 이미 이것을 요구한다. 새 폴더·삭제·이름 바꾸기를
놓을 자리가 기본 꺼짐인 우클릭 메뉴(D-22)밖에 없으면, 껍데기만 있는 상태에서 그
앱의 기본 동작에 도달할 길이 없다.

가름선 아래로만 놓는 것은 껍데기 항목의 위치가 앱마다 달라지지 않게 하기 위해서다.
"폴더 열기는 늘 맨 위"가 유지되면 앱을 옮겨 다녀도 다시 찾지 않는다.

**배제한 대안**

- **네 자리(File·View·Help·뷰 제목줄)를 모두 연다.** View에 앱 항목이 섞이면 화면
  접기·테마가 앱마다 다른 자리에 놓인다. 껍데기를 쓰는 이점이 줄어든다. 배제한다.
- **아무 자리도 열지 않고 키로만 쓴다(옛 상태).** 위 근거대로 배제한다.
- **앱이 껍데기 항목을 빼거나 순서를 바꿀 수 있게 한다.** 앱이 "폴더 열기"를 빼면
  루트를 바꿀 길이 사라지는데, 그것이 앱의 실수인지 의도인지 껍데기가 판단할 수
  없다. 배제한다.
- **이 표면을 v0.2로 미룬다.** 확장 앱(노트북·마인드맵)만의 요구라면 미룰 수
  있으나, 위 근거대로 v0.1의 검증 앱 셋이 이미 요구한다. 배제한다.

## D-32. 앱이 하단 바에 메시지와 진행을 올린다 — 자리와 그리기는 껍데기

**선택**

D-21은 "무엇을 알릴지는 앱이 정하되 어떻게 보일지는 껍데기가 정한다"고 했으나 앱이
부를 자리를 정하지 않았다. 여기서 정한다.

앱이 하단 바 메시지 자리에 **오류·안내 한 줄**을 올리고, **진행 표시**를 켜고 끌 수
있다. 껍데기가 자기 오류·진행(D-21)을 올릴 때 쓰는 것과 같은 자리·같은 모양이다.

- 그 자리는 **한 줄**이다. 껍데기가 올린 것이든 앱이 올린 것이든 **가장 최근 것
  하나만** 보인다. 쌓이는 목록을 두지 않는다.
- 앱이 올린 문구를 껍데기가 고치지 않는다. 모양·색·자리는 껍데기가 정한다.
- 진행은 앱이 켜고 앱이 끈다. 껍데기가 임의로 끄지 않는다.

FR-N10의 "앱이 하단 바에 자기 항목을 붙인다"와는 다른 자리다. 그쪽은 **상주하는
항목**이고 이쪽은 **지나가는 메시지**다.

**근거**

알릴 내용을 아는 쪽은 앱뿐이다 — 커널이 도는 중인지, 파일 복사가 몇 개째인지,
읽기에 실패한 것이 무엇인지는 껍데기가 모른다(INTENT 3). 그런데 그리는 자리는
껍데기에만 있다. 부를 길이 없으면 앱은 화면 안에 자체 표시줄을 만들게 되고, 그것은
D-21이 "떠오르는 알림 상자를 만들지 않는다"로 막으려던 결과와 같아진다.

한 줄에 가장 최근 것만 두는 것은 D-21의 "쌓이는 목록을 두지 않는다"를 그대로
따른 것이다. 껍데기와 앱이 자리를 다투는 규칙을 새로 만들지 않아도 된다.

**받아들이는 단점** — 껍데기 오류와 앱 메시지가 짧은 간격으로 겹치면 앞엣것이
보이지 않고 지나간다. D-21이 이미 "하단 바는 눈에 덜 띄어 놓칠 수 있다"를 알고
고른 것과 같은 단점이라, 여기서 새로 늘어나는 위험이 아니다.

**배제한 대안**

- **앱 메시지 자리를 따로 만든다.** 겹침 규칙이 없어지지만 하단 바가 길어지고,
  껍데기 오류와 앱 오류가 다른 곳에 떠서 사용자가 두 곳을 봐야 한다. 배제한다.
- **메시지를 쌓아 두고 넘긴다.** D-21이 알림 센터를 배제한 이유가 그대로 적용된다.
  배제한다.
- **앱은 FR-N10의 상주 항목만 쓴다(표면을 열지 않는다).** 상주 항목은 상태를
  보이기엔 되지만 "실패했다"·"끝났다"처럼 지나가는 것을 담지 못한다. 배제한다.
- **껍데기가 일정 시간 뒤 앱 메시지를 지운다.** 껍데기가 그 메시지가 아직 유효한지
  판단해야 하는데 알 수 없다. 앱이 끄게 둔다. 배제한다.
