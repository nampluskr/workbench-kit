> 대상: v0.2 Phase 2 — 선택과 포커스 표시 (`WK-053` ~ `WK-057`).
> 요구: `FR-P9` · `FR-F1` ~ `FR-F11`.
> 검토자: OpenAI Codex `gpt-5.6-sol` (구현자 Claude Opus 5의 반대 벤더).
> 필수 통과 Phase가 **아니다** (`PLAN.md` 적대적 검증: 1 · 4 · 7). 새 기능 Phase라 검증은
> 하되(`ADVERSARIAL-REVIEW.md` 3절), 미해결 지적이 다음 Phase 진행을 막지는 않는다.
> 일자: 2026-09-10.

## 3. Round 1 — Critical 0 · Major 3 · Minor 1

| # | 심각도 | 지적 | 처리 |
| --- | --- | --- | --- |
| — | (진행 중 발견) | `F6`이 화면 순서가 아니라 dockview의 **삽입 순서**로 칸을 돈다. 칸을 왼쪽이나 위로 나누면 먼저 보이는 칸이 나중에 온다 | **해결** — 칸을 화면 읽기 순서(위→아래, 왼쪽→오른쪽)로 정렬한다. `V2P2-FR-F1-ORDER` 신설: 탭을 칸의 **왼쪽 가장자리로 끌어** 만든 순서와 화면 순서가 다른 배치를 만들고 `F6`이 왼쪽 칸부터 가는지 본다 |
| R1-1 | Major | **제품 결함.** 저장 안 한 탭의 닫기 버튼을 실제로 누르면(`pointerdown`→`click`) 칸 전체에 걸린 `pointerdown` 처리가 늦게 `focusGroup()`을 실행해, 닫기가 연 **확인 창의 포커스를 도로 빼앗는다.** 기존 검사는 `.click()`만 써서 `pointerdown`이 없었다 | **해결** — 버튼 · 탭 닫기 · 입력칸을 누른 경우는 끌어오지 않고, 지연 실행 시점에 확인 창 · 메뉴가 포커스를 가져갔으면 끌어오지 않는다. `V2P2-DIALOG-FOCUS` 신설(실제 `pointerdown`·`pointerup`·`click` 순서로 dirty 탭 닫기 → 포커스가 확인 창 안) |
| R1-2 | Major | `FR-F11`이 실제로 판정되지 않는다. 선택 배경을 사이드바와 1.3:1로만 보고, hover는 **토큰 문자열 두 개를 비교**할 뿐이라 같은 색을 다르게 적은 경우도 통과한다 | **해결** — hover 색을 탐침 요소로 실제 해석해 사이드바 배경 위에 합성한 **칠해진 색**을 선택 배경과 대비 측정한다(≥1.2). 선택된 커서 행의 테두리와 그 배경 대비도 측정한다(≥3). 선택 배경 대 사이드바 1.3:1 기준은 유지한다 — 6절 남은 위험 |
| R1-3 | Major | `FR-F5`의 "보이는 빈 곳 누르기"가 우회된다. 행 40개로 트리가 넘치는데 `.tree-list`에 직접 클릭을 보내므로, 화면상 누를 빈 곳이 없어도 통과한다 | **해결** — 먼저 모두 접기(`Ctrl+←`)로 실제 빈 곳을 만들고, 마지막 행 아래 좌표를 `elementFromPoint`로 찾아 **행이 아닌 요소**를 그 좌표로 누른다. 그런 지점이 없으면 실패한다 |
| R1-4 | Minor | 에디터 안 `Tab` 검사가 영역만 본다. `Tab`을 삼키고 아무것도 하지 않는 처리도 통과한다 | **해결(방식 변경)** — 처음에는 보이는 텍스트 변화를 요구했으나, monaco의 EditContext 입력은 합성 이벤트로 들어온 타이핑을 처리하지 않아 정상 구현에서도 텍스트가 바뀌지 않았다. 그래서 껍데기가 통제하는 쪽을 직접 본다: 탭의 보기 요소에 보낸 `Tab`이 **`defaultPrevented` 없이 도착**하는지(보기 요소에서는 껍데기 리스너만 막을 수 있다)와 영역 불변을 함께 요구한다. 에디터가 실제로 들여쓰는지는 사용자 재검증 몫이다(6절) |
| — | 검증 우려 | 두 갈래 대조가 통과 여부(참/거짓)만 비교해, 기준 안에서의 관측값 차이는 드러나지 않는다 | **기록만** — 판정 규칙(`SPEC.md` 0절)이 "결과가 다른 항목 0건"이라 현재 대조가 그 문언을 만족한다. 관측값 대조는 6절 남은 위험 |

## 4. 음성 검사

R1-1 수정(버튼·입력칸 누르기 제외, 확인 창·메뉴가 포커스를 가져간 경우 제외)을 되돌리고
재빌드하면 `V2P2-DIALOG-FOCUS`가 **실패**하고, 원복 후 통과한다. 실제 `pointerdown` 순서로
dirty 탭을 닫는 검사가 지적된 결함을 잡는다는 증거다.

| 무엇 | 결과 |

재실행 중 두 가지를 더 고쳤다. `FR-F5`가 빈 곳을 만들려고 트리를 접은 채 두어 뒤 블록이
파일 행을 찾지 못하고 중단됐고(설정 복원 추가), R1-4의 첫 보강(텍스트 변화 요구)은 합성
이벤트로 성립하지 않아 판정 방식을 바꿨다(3절 R1-4).

**판정** — 미해결 Critical 0건, Major · Minor 전건 반영. Phase 2를 닫는다.

## 6. 남은 위험

| 무엇 | 왜 남았나 |
| --- | --- |
| 회색 테마의 선택 배경이 사이드바와 1.68:1 | 검사 기준(1.3)은 넘지만 WCAG 비텍스트 기준(3:1)에는 못 미친다. 회색 테마 색은 v0.1 D-29가 흰색·검정의 보간으로 정한 값이라 이번 Phase에서 바꾸지 않았다. 사용자 재검증에서 구분이 안 된다고 나오면 테마 결정을 다시 연다 |
| 에디터 안에서는 `F6`으로 빠져나올 수 없다 | `F6`을 조건부로 둔 사람 결정(D-10)의 대가다. 트리나 탭 줄을 눌러 영역을 옮긴다 |
| 두 갈래 대조가 관측값을 비교하지 않는다 | 판정 규칙이 통과 여부의 일치를 요구한다. 대비 수치 같은 관측값이 갈래 사이에서 크게 달라도 둘 다 기준을 넘으면 드러나지 않는다 |
| 포커스 · 키보드 검사가 다른 창에 취약하다 | 그리는 창이 포커스를 가져야 하므로, 검토자 실행이나 이전 실행이 남긴 창이 떠 있으면 실패할 수 있다. 실패 시 먼저 남은 테스트 프로세스를 확인한다 |
| 끌기 · 누르기는 합성 이벤트다 | 실제 마우스 동작은 사용자 재검증(`docs/user-tests/`)에서 확인한다 |
| 에디터가 `Tab`으로 실제 들여쓰기를 하는지 | monaco의 EditContext 입력은 합성 이벤트의 타이핑을 처리하지 않아 자동 검사로 볼 수 없다. 자동 검사는 껍데기가 `Tab`을 막지 않는다는 것까지만 판정한다(R1-4). 실제 들여쓰기는 사용자 재검증에서 확인한다 |
